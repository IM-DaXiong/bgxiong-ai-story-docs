设计一个既能灵活适配各种云端视频 API（如 Runway Gen-3、Kling、Sora 等），又能对每次生成的提示词和结果进行“版本控制”的底层数据架构，是决定你的 Genesis Engine 能否从“好玩的工具”蜕变为“生产力平台”的关键。

在处理这种高成本、高试错率的 AI 视频生成任务时，最忌讳的就是“覆盖保存”。一旦覆盖，用户就永远找不回昨天那个完美的提示词了。

作为架构师，我建议你引入 “Git for Video” (基于快照的不可变版本控制) 设计理念。以下是详尽的架构与数据组织方案：

一、 核心思想：意图与执行的解耦 (Decoupling Intent from Execution)
你的系统必须将“导演意图”（分镜里写了什么）和“执行代码”（发给 API 的具体 JSON）彻底分开。

整个数据流分为三层：

元数据层 (Meta Layer)： 用户在 UI 上看到的场次、分镜、剧本。

配置层 (Profile Layer)： 选择哪个大模型？长宽比多少？运动幅度（Motion Score）多大？

快照层 (Commit Layer)： 真正的版本控制，记录每一次点击“生成”时的绝对状态。

二、 数据库/数据结构设计方案
不要在“分镜”这个数据表里直接存生成的视频 URL。你需要引入一个叫做 Generation_Task (生成任务记录) 的实体。

1. 镜头元数据 (Shot Metadata)
这是用户在工作台上编辑的内容，是不断变化（Mutable）的。

JSON
{
  "shot_id": "shot_001",
  "scene_id": "scene_12",
  "director_intent": {
    "action": "孙行者从天而降，金箍棒砸碎地面",
    "camera_movement": "Tilt down, fast speed",
    "subject_image_ref": "actor_sun_01.jpg" // 关联的演员/角色图
  }
}
2. 渲染配置文件 (Render Profile)
解决“灵活配置”的问题。用户可以选择不同的 API，或者保存自己的常用参数集。

JSON
{
  "profile_id": "preset_kling_action",
  "api_provider": "Kling_V1.5",
  "parameters": {
    "aspect_ratio": "16:9",
    "duration": "5s",
    "motion_bucket": 120, // 动作幅度
    "prompt_template": "Cinematic shot, {{camera_movement}}, {{action}}, 4k, hyper-detailed."
  }
}
3. 核心：生成快照记录 (Generation Commit) - 版本控制的灵魂
极其重要： 当用户点击“生成”时，程序必须立刻创建一个**不可变（Immutable）**的快照记录。

JSON
{
  "task_id": "task_9a8b7c6d", // 唯一的版本号
  "shot_id": "shot_001",
  "timestamp": "2026-04-05T10:00:00Z",
  "status": "COMPLETED", // PENDING, RUNNING, COMPLETED, FAILED
  
  // 1. 锁定当时的输入（防止用户后来改了分镜，导致不知道这个视频是怎么来的）
  "snapshot_intent": { ... }, 
  
  // 2. 锁定当时的配置
  "snapshot_profile": { ... },
  
  // 3. 最终编译发给 API 的确切 Payload（用于 debug 和复现）
  "compiled_api_payload": {
    "prompt": "Cinematic shot, Tilt down, fast speed, 孙行者从天而降...",
    "image_url": "https://...",
    "cfg_scale": 7.5
  },
  
  // 4. API 返回的结果
  "result": {
    "video_url": "https://api.provider.com/video_v1.mp4",
    "cost": 0.50 // 记录消耗，非常重要！
  },
  
  // 5. 用户标记
  "is_starred": true // 用户是否将这个版本标记为“最终采用”
}
三、 提示词模版引擎 (Prompt Templating)
为了应对不同 API 对提示词口味的不同（比如有的吃自然语言，有的吃 Tag 堆叠），你需要在后端实现一个模板编译器。

当执行生成时，系统会做变量替换：

读取 Render Profile 中的模板字符串：[风格] {{action}}, 摄影机: {{camera_movement}}。

注入 Shot 的数据。

如果有关联的角色图（Image Prompt），自动将其转为 API 需要的 Base64 或 URL 格式附加到 Payload 中。

这种设计下，如果你明天想接入一个全新的视频大模型，你连代码都不用改，只需要在数据库里新建一个 Render Profile 即可。

四、 UI 交互建议：如何在前端呈现“版本”？
你的无限画布或者详情面板里，对于某一个“分镜（Shot）”，应该有这样的交互：

版本抽屉 (Version History)： 点击某个镜头，侧边栏滑出一个“历史记录”。

列表展示： 列出该镜头下的所有 Generation_Task（时间、使用的模型、缩略图、消耗的积分）。

设为首选 (Set as Active)： 用户点击某一个历史版本上的星号，系统就将这个视频的 URL 绑定为当前分镜的主视频。

参数复原 (Revert to this setting)： 如果用户觉得 V2 版本的动作最好，点击“复用此参数”，系统自动把 V2 的 snapshot_intent 覆盖回当前编辑区。

五、 架构师避坑指南
Webhook 异步回调： 云端视频生成通常需要几分钟。你的系统不能一直阻塞等待（Polling 轮询很浪费资源）。必须设计一个 Webhook 接收端点，让 API 生成完毕后主动通知你的服务器，更新 Generation_Task 的状态，并通过 WebSocket 推送给前端 UI（让进度条变成绿色）。

既然是客户端软件（尤其是基于你目前的 Rust/Tauri 架构），本地存储的灵活性和安全性就是你的核心优势。在这种情况下，你可以模仿 Git 的版本管理思想，但在实现上要更符合影视制作的“重资产”特性。

针对**“全本地存储”、“灵活配置”和“版本一致性”**，我为你设计了一套名为 “镜像快照仓库（Snapshot Vault）” 的架构方案：

1. 存储结构：基于“工程目录”的本地文件系统
不要把所有东西都塞进一个巨大的 SQLite 数据库，那样一旦文件损坏，整个工程就废了。建议采用 “数据库索引 + 结构化文件夹” 的方式：

数据库 (index.db): 仅存储关系映射、提示词文本、模型配置参数（轻量级，方便检索）。

资源文件夹 (Assets/): * /shots/shot_001/images/: 存储该分镜的所有参考图、底图。

/shots/shot_001/versions/: 关键！每个生成的视频，都以其 TaskID 命名存储在这里。

/cache/: 存储云端下载的临时预览图。

2. 灵活配置：实现“渲染预设 (Render Presets)”
为了让用户在不同云端 API 之间无缝切换，你需要设计一个 Provider 适配器层：

JSON 配置预设： 允许用户保存自己的“配置包”（例如：“可灵-动作增强版”、“Runway-高动态版”）。

动态字段映射：

用户在 UI 上配置通用参数（如：动作幅度 1-10）。

你的适配器脚本根据选择的 API，自动将其翻译为特定的参数（如：Kling 的 motion_score 或 Runway 的 motion_bucket）。

3. 版本管理：不可变的“任务快照”逻辑
这是保证“各个版本都能找回来”的核心。用户点击“生成”时，执行以下逻辑：

Freeze（冻结）： 抓取当前 UI 上该分镜的所有状态（当前提示词、引用的图片路径、当前选中的模型配置）。

Hash（取值）： 将这些状态通过哈希算法生成一个唯一的 Version_Hash（类似 Git 的 Commit ID）。

Local Record（本地记录）： 在数据库中新建一条记录，并将生成的视频文件下载到本地 /versions/[Version_Hash].mp4。

Sidecar File（边车文件）： 在视频旁边生成一个同名的 .json 记录文件。这样即使数据库丢了，扫描文件夹也能重建版本历史。

4. 针对客户端性能的优化建议
由于你是 4090 + 128G 内存 的怪兽级配置，你可以让客户端做更多“重活”：

本地向量检索 (Local RAG): 你的 100 部经典电影 JSON 库可以完全放在本地。用户写提示词时，客户端本地调用轻量级模型（如 Llama-3-8B）进行实时提示词增强，无需联网。

多版本并排对比 (A/B Testing): 既然视频在本地，你的 UI 可以支持“分屏播放”。左边放 V1 版本，右边放 V2 版本，让用户直观对比哪个云端 API 的效果更好。

断点续传与同步： 云端 API 回调可能很慢，你的本地任务队列要支持“重启软件后自动查询”。利用 Tauri 的后台进程监听 API 状态，哪怕软件关了，后台小图标也可以在生成完成时弹出 Windows 通知。

5. 架构师的“终极灵活性”小技巧：
在你的提示词组织逻辑中，引入一个 “混合提示词栈 (Prompt Stack)”：

层 1 (Base): 自动从你那 100 部电影库里提取的风格词（如：Deakins lighting）。

层 2 (Shot): 故事板里定义的动作词（如：Running through fire）。

层 3 (User): 用户在生成对话框临时加的词（如：More sparks）。

生成的提示词 = Base + Shot + User。
这样用户既能享受你系统自带的大师级调教，又能保留极高的自由发挥空间。

我们可以利用这种“原样存储”的优势，在客户端构建一个极速、专业且具备工业级溯源能力的视频管理系统。

以下是针对“原样保持”策略的深度架构优化：

1. 建立“边车”索引文件（Sidecar Metadata）
由于视频文件很大，频繁读取视频头信息会产生 I/O 开销。

做法： 每个视频文件（如 v1_hash.mp4）生成时，同步创建一个 v1_hash.json。

包含内容： 除了提示词和模型参数，还要包含视频指纹（Hash）、原始分辨率、帧率、色彩空间（Rec.709/HLG）以及云端 API 的原始任务 ID。

意义： 这样你在 UI 上预览版本列表时，可以秒开信息，无需加载大视频文件。

2. 内存映射预览（RAM-Cached Preview）
既然有 128G 内存，不要浪费。

优化方案： 在 Tauri 后端建立一个内存缓存池。

逻辑： 当用户在无限画布上缩放时，系统预先将当前场次涉及的所有视频片段的“前 1 秒”或“首帧”载入内存。

效果： 用户拖动时间线或切换版本时，画面能够实现 0 延迟 瞬时切换，这种丝滑感是云端平台无法比拟的。

3. 基于存储路径的“硬链接”版本管理（Hard Link Optimization）
如果用户在不同场次复用了同一个分镜生成结果：

逻辑： 检查哈希值。如果本地已存在相同视频，不再重复下载或拷贝，而是使用文件系统的硬链接（Hard Link）。

收益： 物理上只占用一份空间，但在用户看来，两个场次的文件夹里都有这个视频。

4. 视频“血统”追踪（Video Lineage Tracking）
原样保持的最大价值在于溯源。

架构设计： 在 UI 上提供一个“溯源面板”。当用户选中一个本地视频，系统能反向推导出：

它是哪一天生成的？

当时用的是哪张演员参考图（Actor Image）？

参考了哪部经典电影的风格（如《教父》的 JSON 参数）？

导出功能： 当用户最终要把视频导入 DaVinci Resolve 时，你的系统可以自动生成一个 CSV 或 OTIO 列表，将这些原始 Prompt 作为“元数据”写入视频的备注列。

5. 客户端本地搜索优化（Local Search Engine）
随着生成的视频越来越多（可能达到几百 GB），“找视频”会变成痛点。

架构： 利用 Rust 的高性能，在本地对所有 Sidecar JSON 建立全文索引。

功能： 用户可以搜索“那个背景有火的、用可灵生成的、带孙行者的视频”，系统能瞬间定位到本地文件夹中的具体文件。

6. 自动化的“代理文件”生成（Optional Proxy Workflow）
虽然原样保持，但 4K 视频在无限画布上多路同时播放压力很大。

建议： 后端利用 FFmpeg 悄悄生成一个极小的 720P 低码率预览版（Proxy）。

逻辑： 画布操作时看预览版，点击“全屏查看”或“导出”时自动调用原片。这能保证你的软件在任何时候都极其流畅。

架构师总结
你的“原样保持”策略配合顶级硬件，让 Genesis Engine 拥有了本地私有化素材库的属性。这不仅是版本控制，更是一个**“导演的视觉灵感库”**。


要实现从你的“故事板/分镜”到“PR/达芬奇时间线”的无缝对接，核心在于将 AI 生成的非线性资产（各版本的视频）转化为标准的线性剪辑数据（Metadata + Timeline）。

在客户端架构中，实现“一键导出 XML”的最佳路径如下：

1. 核心导出架构：从 DAG 到 Timeline
由于你的故事板已经有了场次、分镜、版本号以及对应的本地视频路径，你只需要一个**“导出编译器”**，将这些数据映射到 FCPXML (Final Cut Pro XML，达芬奇和 PR 均通用) 或传统的 Premiere XML 格式。

逻辑映射：

Project (项目) -> 你的 Genesis 工程。

Sequence (序列) -> 你选定的剧集或场次集合。

Track (轨道) -> V1 轨放置选定的视频，V2 轨可以放置故事板参考图（可选）。

Clip (剪辑) -> 对应你本地 /versions/ 下的原始视频。

Markers (标记) -> 关键！将 AI 提示词、导演备注写入剪辑标记。

2. 实现方案：推荐使用 OpenTimelineIO (OTIO)
作为架构师，我不建议你手动去拼接复杂的 XML 字符串。推荐在你的 Rust 后端或通过 Python 脚本集成 OpenTimelineIO。

流程：

收集数据： 遍历用户在 UI 上“打星”选中的视频版本，获取它们的本地绝对路径、帧率、持续时间。

构建 OTIO 模型： 创建一个 otio.schema.Timeline，将每个视频按顺序添加进 Track。

适配器转换： 使用 OTIO 提供的适配器（Adapter），一键将内存中的模型转换为 .xml (Premiere) 或 .fcpxml (DaVinci)。

3. XML 导出的“工业级”细节（必做项）
为了让用户在 PR/达芬奇里打开时“像呼吸一样自然”，你需要处理好以下细节：

绝对路径与相对路径： XML 中记录的视频路径必须准确。建议导出时询问用户：“是否将素材拷贝至导出文件夹？”。如果选是，将视频原样拷贝过去并使用相对路径；如果选否，直接记录当前电脑上的绝对路径。

帧率对齐（Frame Rate）： 确保 XML 定义的序列帧率（如 24fps）与 AI 生成视频的原始帧率完全一致，否则会出现音画不同步或跳帧。

元数据注入（Metadata）：

将 Prompt（提示词） 写入剪辑的 Description 字段。

将 镜头参数（如 85mm, Low Angle） 写入剪辑的 Scene/Shot 字段。

这样导演在达芬奇里调色时，低头就能看到这个镜头的创作初衷。

4. 增强型功能：多版本轨道导出（Multi-Track Versions）
这是一个非常受专业用户欢迎的功能：

方案： 导出的 XML 不只给一层轨道。

实现： V1 轨放用户选中的“最终版”，V2 轨放“备选版 1”，V3 轨放“原始故事板图”。

效果： 用户在达芬奇里一按快捷键就能切换不同版本，极大地提高了剪辑决策效率。

5. 给你的“一键导出”按钮添加一个“打包检查器”
在导出前，系统应自动执行以下检查：

文件完整性： 检查选中的原始视频文件是否还在本地硬盘（没被用户手动删掉）。

分辨率一致性： 如果场次里有 4K 也有 1080P，提醒用户序列将以何种规格建立。

生成 OTIO 报告： 导出一个简单的 HTML 网页，列出本场次所有镜头的参数，作为纸质分镜单存档。

总结
在你的客户端软件中，增加一个 Export to NLE (XML) 的功能，本质上是把你本地的 JSON 数据库关系 翻译成 影视工业标准协议。
