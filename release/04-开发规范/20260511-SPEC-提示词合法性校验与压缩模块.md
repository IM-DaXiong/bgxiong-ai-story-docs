## 0. 导读：「现在是这样吗？」

**初稿阶段的 SPEC 并不是严格的「仅针对模型」**：叙述、示例与改造清单明显围绕 **生图管线**（`cast_portrait`、`image_gen_prepare`、`generate_image`），容易让人误以为模块属于「图像业务层」。

**升级后的定位（本文件为准）**：

| 维度 | 说明 |
|------|------|
| **长度与危险区** | **只读** `model_capabilities::normalize_provider_kind` + `max_prompt_chars_for_kind` + `prompt_threshold_ratios`。业务 **不得**自建一套「800 字」等硬编码。 |
| **压缩话术（LLM system prompt）** | 由 **`PromptCompressionIntent`**（模态/用途）决定，用于指导 LLM **如何无损压缩**，**不改变**数值上限。 |
| **谁调用** | 任意在 **HTTP / 本地推理前** 要把一段 **字符串** 交给 **某一 `provider_kind` 模型** 的管线：生图、生视频、文本对话、TTS/音效说明等 **只要该字段受 `max_prompt_chars_for_kind` 约束**，就应通过同一入口（或薄封装）。 |

因此：**模块针对的是「当前选中的目标模型 + 将要提交的文本字段」**，不是针对「演员 / 场次 / 分镜」等业务名词；业务只是 **传入正确的 `provider_kind` 与意图枚举**。

## 1. 问题复盘

### 1.1 现状

| 层 | 位置 | 状态 |
|----|------|------|
| 能力边界数据 | `model_capabilities.rs` → `normalize_provider_kind`、`max_prompt_chars_for_kind` | **已覆盖多类**：如 `image_*`、`video_volc_jimeng_t2v_*`、`video_seedance_2_0`、`text_*` 等；**数值 SSOT** |
| 危险区阈值 | `model_capabilities.rs` → `prompt_threshold_ratios` | **填报规则与逐通道依据见附录 B**。代码现状多为 `(None,None)`：**须在文档层「补全」引用与状态**；仅当有官方证据或备案观测工单时，才允许改代码为非空比例 |
| 压缩执行（图） | `image_gen_prepare.rs` → `prepare_generate_image_request` | 与生图强耦合；依赖 `prep_text`，且调用链上曾被 **`use_text_extract` 误伤** |
| 零散压缩 | `prompt_compressor.rs` | **Clips 视频等路径仍在使用**，与生图侧逻辑 **分裂**；需 **迁入统一模块后停用** |
| 任务进度 | `ai_task::update_progress_merge` | 可用；统一模块应对 **可选 `job_id`** 写入同一套 `phase` 协议 |

### 1.2 典型缺陷（示例：演员肖像）

`cast_portrait.rs` 曾将「文本服务」绑定在 **`use_text_extract`** 上，`false` 时不传文本服务 → 生图侧长度压缩无法调用 LLM。**根因是调用策略错误，不是「只有生图需要压缩」。**

## 2. 设计目标（模型中心 · 跨模态）

| # | 目标 | 反模式（不做） |
|---|------|----------------|
| G1 | **单一真相**：字符上限与危险区 **仅**来自 `model_capabilities`， keyed by **规范化后的 `provider_kind`** | 业务层复制「800/3200」等魔法数字 |
| G2 | **校验 +（必要时）LLM 压缩 + 进度** 在同一模块内完成，对外 **一次 await** | 图走一套、视频再走一套硬编码 tokenizer |
| G3 | **压缩用工模型**（`AiServiceConfig`）由调用方按 **用户所选文本服务商** 传入，与「是否做视觉关键词提取」等 **业务开关解耦** | 再用业务布尔值推导能否压缩 |
| G4 | 最多 **2 次** LLM 压缩尝试；每次 **`tracing` + `dev_log_final_prompt` +（若有）任务进度** | 静默截断、无限重试 |
| G5 | 两次失败 → **`Err` 返回调用方**；由 UI/管线决定呈现（本模块不代替产品做「凑合发出」） | 在模块内擅自改通道或未选模型 |
| G6 | **`PromptCompressionIntent`** 只影响 **压缩指导语**，不参与 **是否超限** 的判定 | 按「演员/场次」分支写死上限 |
| G7 | 旧 `prompt_compressor`、生图内嵌压缩逻辑 **收敛到本模块** 后移除重复实现 | 长期双轨维护 |

## 3. 概念模型

### 3.1 输入三要素

1. **`prompt`**：即将参与 **长度判定 / 压缩** 的那段字符串。  
   - **必须**与下游实际发往模型的正文 **一致**（对生图而言：即 **`normalize_image_prompt_for_dispatch` 之后**、进入 HTTP 包体前的正文；见 **§7.2**）。  
   - **`model_prompt_prepare::ensure_prompt_for_model` 内部不调用** `to_natural_language_prompt`、**不解析** `RAW_PROMPT_PASSTHROUGH_PREFIX`：避免把「仅生图适用」的规则塞进跨模态模块，也避免与视频/文本链路语义混杂。
2. **`provider_kind`**：**目标模型** 在能力表中的 canonical id（可先传 UI/后端别名，模块内 **`normalize_provider_kind`**）。
3. **`intent: PromptCompressionIntent`**：告知压缩 LLM「这段文字在服务什么场景」，**不改变** `l_max`。

### 3.2 `PromptCompressionIntent`（建议 Rust 枚举）

| 枚举值 | 用途 | system prompt 侧重点（示例方向） |
|--------|------|----------------------------------|
| `ImageSceneDescription` | 文生图 / 图生图 / 分镜画面描述 | 保留主体、光影、风格、构图；削冗余对白 |
| `VideoMotionDescription` | 视频运动、镜头、主体与节奏描述 | 保留动作、镜头语言、主体连续性 |
| `ChatOrCompletionPayload` | 对话 / 补全中要提交的 **user 片段**（若该请求受限于模型上下文产品策略） | 保留意图与约束；削例证与重复 |
| `AudioScriptOrCue` | TTS 朗读稿、音效/配乐文字说明等 | 保留可念读内容与语气提示；削舞台说明 |

若暂无细分必要，可先实现 **Image / Video / GenericText** 三档，与上表映射。

#### 3.2.1 四种 intent 的 system prompt 差异有多大？（实现结论）

| 维度 | 结论 |
|------|------|
| **总体** | **不是**四套完全独立的压缩管线（同一套 `chat_completion`、同一计数口径、同一输出契约）。差异集中在 **system 正文中一段「场景约束」**（约占总篇幅 **30%～40%**），其余为 **共用骨架**。 |
| **实现复杂度** | **低到中等**：推荐 **`format!(COMMON_SHELL, max_chars, intent_paragraph)`** 或 `match intent { ... }` 拼接 **常量字符串**；无需为 Audio 单独换模型或换 API。 |
| **何时需要再细化** | 若线上评测表明某 intent **频繁破坏关键信息**（例如 TTS 丢了人称、视频丢了镜头号），再在 **该 intent 段落内**增量规则（仍不建议拆成完全异构 prompt）。 |

**与 `image_gen_prepare` 的关系**：`ImageSceneDescription` 的模板应与当前 `compress_prompt_for_image_cap` 的画面对齐，便于迁移时行为可比。

### 3.3 「音频」如何纳入

本仓库多数 **音频链路** 的最终载体仍是 **文本**（台词、旁白、音效描述）。**不设单独「音频 magic limit」**：

- 若未来 `max_prompt_chars_for_kind` 为某 **`audio_*` 或 TTS `provider_kind`** 配置了上限，则 **同一套 `check_length` + compress** 生效；
- 若表项为 `0`（未声明），模块 **视为无明确上限、跳过压缩**（与现 `model_capabilities` 语义一致）。

## 4. 模块架构

```
┌─────────────────────────────────────────────────────────────────┐
│ 调用方（任意业务：仅负责拼 prompt、解析用户选的「目标模型」）           │
│  例：cast / role / actor / scene / segment 生图；Clips 生视频；        │
│       文本命令写 user 消息；TTS 文案提交 等                            │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             │ ensure_prompt_for_model(
                             │   prompt,
                             │   provider_kind,   // 目标模型 → SSOT
                             │   intent,          // 仅影响压缩话术
                             │   text_service,    // 用户选的「压缩用工」LLM
                             │   job_id, db,
                             │ ) -> Result<String, String>
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  model_prompt_prepare.rs（建议文件名；下文亦称「本模块」）             │
│  ┌─────────────────┐     ┌───────────────────────────────────┐  │
│  │ check_length()   │────▶│ model_capabilities::               │  │
│  │                  │     │ normalize_provider_kind             │  │
│  │                  │     │ max_prompt_chars_for_kind           │  │
│  │                  │     │ prompt_threshold_ratios               │  │
│  └────────┬─────────┘     └───────────────────────────────────┘  │
│           │ ok → 返回原文                                           │
│           │ need compress ↓                                         │
│  ┌────────▼─────────────────────────────────────────────────────┐ │
│  │ compress_with_retry(intent, …)  // LLM ×≤2，日志 + 进度       │ │
│  └──────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

> **命名说明**：若团队更希望保留 `prompt_validator.rs` 文件名亦可；需在模块头注释写明「职责为 **模型约束下的文本就绪**，非业务校验器」。

> **生图路径**：业务管线 **不**直接画箭头到 `ensure_prompt_for_model`；应先进入 **`generate_image`**，由其在内部 **`normalize_image_prompt_for_dispatch` → ensure**（§7.2）。本图省略该分叉以保持跨模态共性。

## 6. 核心 API（Rust 示意）

### 6.1 对外函数

```rust
//! 模型约束下的提示词就绪：长度来自 model_capabilities，压缩话术来自 PromptCompressionIntent。

#[derive(Debug, Clone, Copy)]
pub enum PromptCompressionIntent {
    ImageSceneDescription,
    VideoMotionDescription,
    ChatOrCompletionPayload,
    AudioScriptOrCue,
}

/// 若长度合规则返回 trim 后原文；否则 LLM 压缩（最多 2 次）。
///
/// **`trim` 后为空**：返回 `Ok(String::new())`，**不**做长度判定与压缩（与 `prepare_generate_image_request` 在 `n==0` 时不触发压缩一致）。「禁止空描述」属于 **业务命令/管线** 校验，见 §6.3 管线表。
///
/// **前置条件**：非空时，`prompt` 必须是 **目标链路已完成与本请求一致的预处理后的正文**（生图 = §7.2 规范化之后；视频/文本 = 该 HTTP 字段最终稿）。本函数 **不负责** `to_natural_language_prompt` / RAW passthrough。
///
/// - `provider_kind`：目标模型（生图/视频/文本/TTS 等在能力表中的 key）
/// - `intent`：仅影响压缩用 system prompt，**不改变** l_max
pub async fn ensure_prompt_for_model(
    prompt: &str,
    provider_kind: &str,
    intent: PromptCompressionIntent,
    text_service: &AiServiceConfig,
    job_id: Option<&str>,
    db: &DbState,
) -> Result<String, String>;
```

内部：`let pk = model_capabilities::normalize_provider_kind(provider_kind);`，后续 **`check_length`** / 日志 / `dev_log_final_prompt` 的 `ai_provider` 字段 **一律用 `pk`**，便于与能力表 grep 对齐。

### 6.2 `build_compress_system_prompt(max_chars, intent)` — 共用骨架 + 分模板正文

#### 6.2.1 共用骨架（所有 intent 相同，`{max_chars}` 为本次尝试的目标上限）

下列三段依次拼接：**固定前缀 → intent 专属段落（§6.2.2）→ 固定后缀**。实现时可将前缀/后缀提成常量，仅 `match intent` 替换中间一段。

**前缀（FIXED_PREFIX）**

```
你是文本压缩编辑。用户的原始内容在紧随其后的 user 消息中给出。
请将内容压缩为不超过 {max_chars} 个 Unicode 标量的单一终稿（计数方式与 Rust 字符串的 chars().count() 一致：每个汉字、拉丁字母、数字、标点各计 1；组合 emoji 可能占多个标量）。
```

**后缀（FIXED_SUFFIX）**

```
保持原文语言（中文输入则输出中文，英文输入则输出英文）。不要输出标题、引号、序号、Markdown、代码块或任何解释性前后缀；只输出压缩后的正文一段。
```

#### 6.2.2 四种 intent 专属段落（仅中间一块不同）

以下为 **推荐默认文案**（中文）；若产品微调，须在 PR 说明评测结论。**第二次尝试**可在 **user** 侧追加反馈（§6.3），一般 **不必**重写整块 system——除非 AB 测试表明需要。

---

**`ImageSceneDescription`**（对齐当前 `image_gen_prepare::compress_prompt_for_image_cap` 语义）

```
压缩目标用于 AI 绘画（文生图/图生图）的画面描述。请保留：主体对象、环境、场景、风格、光照、色彩、构图与关键材质；删除：剧情对白、舞台指示、重复堆砌、括号内的次要说明及与画面无关的叙事。合并近义形容词，避免同义反复。
```

---

**`VideoMotionDescription`**

```
压缩目标用于 AI 视频生成的运动与镜头描述。请保留：主体与动作、镜头运动（推拉摇移等）、节奏与时间顺序、场景/主体连续性、关键道具与冲突点；删除：静态绘画才需要的细节堆砌、与运动无关的长背景散文、重复镜头形容词。若存在明确镜头分段且字数仍超限，优先保留首尾与转折点。
```

---

**`ChatOrCompletionPayload`**

```
压缩目标为即将提交给对话/补全模型的用户正文片段。请保留：用户意图、任务约束、必须遵守的格式或输出结构要求、关键实体名与数值；删除：冗长例证、重复论证、与当前请求无关的背景故事、多余礼貌寒暄。不要擅自添加模型从未给出的新约束。
```

---

**`AudioScriptOrCue`**

```
压缩目标为朗读稿、配音说明或音效/配乐文字 brief。请保留：适合口播的句式、角色语气或情感提示（若原文有）、停顿/重音标记（若原文使用且对合成有用）、音效类型关键词（如「脚步声」「雷雨」）；删除：纯视觉构图与调色描述、分镜号与摄像机参数、与听感无关的舞台调度长句。勿把台词改成第三人称叙事摘要除非原文如此。
```

#### 6.2.4 差异量级小结

| intent | 相对 Image 模板 | 说明 |
|--------|-----------------|------|
| `ImageSceneDescription` | 基线 | 与现网生图压缩话术一致 |
| `VideoMotionDescription` | **中等**：替换「保留/删除」清单 | 强调时间顺序与镜头，而非光影材质 |

### 6.3 长度判定与第二次尝试（实现要点 · 与现状对照）

#### 与当前 `image_gen_prepare` 的差异（避免误解）

| 项目 | 仓库现状（`compress_prompt_for_image_cap`） | 本 SPEC 目标（`compress_with_retry` / `ensure_prompt_for_model`） |
|------|---------------------------------------------|-------------------------------------------------------------------|
| 调用次数 | **仅 1 次** `chat_completion`，无循环 | **最多 2 次**（第一次失败或超长则再试） |
| 第一次略超长 | 依赖后续 **`chars().take(effective_limit)`** 在 `prepare_generate_image_request` 尾部截断（见 `image_gen_prepare.rs`） | SPEC **G5** 倾向由模块策略决定：默认 **不**靠静默截断收尾时，第二次应 **再压一遍** |

因此：**「第二次 + 放宽 5%」并非现有代码行为**，而是新模块引入的策略；文档必须与数学含义、产品目标对齐，否则易写成 **无效参数**。

#### 「放宽 `min(ceil(target×1.05), l_max)`」何时有用、何时 **完全无效**

记第一次基准目标为 **`target`**（通常为 **`L_safe`**（危险区）或 **`l_max`**（超限））。

- **当 `target == l_max`（最常见的超限压缩）**  
  `min(⌈l_max × 1.05⌉, l_max) = l_max` → **数值上与第一次相同**，不存在「放宽上限」这回事。  
  **结论**：第一次若输出 **803 字而目标是 800**，第二次 **不能把合法上限抬高到 805**（上游仍是 **`l_max`**）。放宽 5% **无法覆盖**「只差几个字符」这一类偏差。

- **当 `target = L_safe < l_max`（危险区预防性压缩）**  
  `min(⌈L_safe × 1.05⌉, l_max)` **可能严格大于 `L_safe`**，但仍 **`≤ l_max`**。此时略有含义：**允许压缩模型少砍一点字**，避免第一次贴 `L_safe` 砍得过狠；这与「略超几个字符」是 **不同问题**。

#### 更合理的第二次策略（推荐写进实现）

**主手段**：**保持与第一次相同的 `attempt_target = N`（不得超过 `l_max`）**，更换 **更强、更明确的字数指令**，而不是依赖 5%：

1. **反馈式 user 补充**：第二次 user 须包含机器可读摘要，例如：「你上次输出约 **{n}** 个 Unicode 标量（`chars().count()`），超过上限 **{N}**。请重新压缩，**输出必须 ≤ {N}**，只输出正文。」  
2. **system 强化**：重复 **计数口径**（Unicode 标量 / `chars().count()`，与生图通道一致）；可加一句「若不确定请先缩短再输出」。  
3. **解码**：第二次可将 **`temperature` 略低于第一次**（如 0.25 → 0.15），减少边界抖动（可选，非必须）。

**关于 5%（降级为可选、窄适用）**：仅当 **`target < l_max`** 且产品确认「宁可更接近上限也不愿过短」时，可在第二次使用 **`attempt_target = min(⌈target×1.05⌉, l_max)`**；**不得**将其宣传为解决「第一次刚好超几个字」的通用方案——那种情况只能靠 **同 N 重试 + 更强指令**（或接受下游硬性截断的产品决策，见 §6.8 **`PromptLengthPolicy`**）。

#### 其它要点

- **`l_max == 0`**：`Ok` 跳过长度逻辑（与 `model_capabilities` 注释一致）。

#### 空 prompt：`ensure_prompt_for_model` 与各管线容忍度（仓库核对）

**模块层（推荐契约）**

| 行为 | 说明 |
|------|------|
| **`prompt.trim().is_empty()`** | 返回 **`Ok("")`**：不调用 LLM 压缩、不写「超限」类 `Err`、不要求配置文本服务 **仅为压缩**。 |
| **与 `image_gen_prepare` 对齐** | `prepare_generate_image_request` 内 **`n = params.prompt.chars().count()`** 为 0 时 **`needs_compress`** 为假，直接 **`Ok(())`**；**不因空串报错**。`enforce_no_watermark_constraint` 对空 `prompt` **早退**，亦不报错。 |
| **厂商/API** | 「仅参考图、零字描述」是否合法由 **具体通道与 HTTP 层**决定；**不在本模块一刀切拒绝**。 |

**业务管线层（是否在进 `generate_image` / `ensure` 之前就拒绝空描述）**

以下依据 **当前 Rust 实现**（若前端另有校验，仍应以服务端为准）：

| 入口 / 管线 | 对用户「零字描述」的容忍 | 代码依据（摘要） |
|-------------|--------------------------|------------------|
| **`cast_portrait_still_pipeline`** | **不允许** | `raw_key_info.trim()` 空 → **`Err("提示词为空…")`**，与是否有参考图无关。 |
| **`actor_portrait_pipeline`** | **不允许** | `key_info` 与 `image_prompt` **皆**空 → **`Err("提示词为空…")`**。 |
| **`role_portrait_pipeline`** | **不允许** | `user_prompt_from_ui` 空 → **`Err("请先在界面输入角色定妆提示词…")`**。 |
| **`scene_concept_image_pipeline`** | **通常非空** | `final_prompt` 至少拼接 **「【约束】+ 画幅/风格行」**；即使用户 AI 稿为空，送去模型的串往往仍含模板块（再经 `to_natural_language_prompt`）。 |
| **`commands/image/commands/image_gen.rs`（通用生图 IPC）** | **允许把空串传到 `generate_image`** | 未见对 `prompt` 非空的强制校验；**厂商是否接受「空 + 参考图」**未在本模块统一拦截。 |
| **`clips/commands/video_submit.rs`** | **可出现空串** | 各段 prompt 全空时 `raw_prompt` / `final_prompt` 可为 **空**；是否报错取决于 **视频 API**，当前片段 **未**单独校验非空。 |

**文档结论**

- SPEC **不再**规定「空 prompt → `ensure_prompt_for_model` 一律 `Err`」，否则会与 **`image_gen_prepare` 现状**及 **潜在「仅参考图」IPC** 路径冲突。  
- **演员 / 角色定妆等强交互管线**：继续由 **各自 pipeline / command** 保证「用户必须有描述」，**先于** `ensure` 失败即可。  
- 若未来某产品明确支持 **「合法零字 + 仅参考图」**，只需保证 **编排顺序**仍为：**单次 naturalize → `ensure`（空则直通）→ HTTP**，无需改模块语义。

初稿中的 `PromptValidation` 枚举若对外仅返回 `String`，**不必**留在公开 API；可删除或作为内部调试结构。

### 6.5 `resolve_effective_text_service` 做什么？（仓库现状：`commands/ai_common.rs`）

压缩用工 **不是**魔法全局单例，而是由本函数从 **`AppConfig`** + **`AiServiceOverride`** 合并得到 **`AiServiceConfig`**：

| 步骤 | 行为 |
|------|------|
| 本地模型覆盖 | 若 override 声明 `TEXT_KIND_LOCAL_MODEL`，要求 override 内模型已指明，否则 `Err`。 |
| 读默认文本段 | 取 `cfg.api.text_gen`，且 **`text_gen_section_is_effectively_set`**（`base_url` / `api_key` / `model` / AK-SK 等至少一类非空）才算「有配置」；否则等价于从空默认合并 override。 |
| 凭证 | **`creds_sufficient_for_request`**：无足够凭证则 `Err`（文案含「未配置 [api.text_gen]…」）。 |
| 模型名 | **`merged_text_model_ready`**：`model` 非空，否则 `Err`（文案含「未指定文本模型…」）。 |

因此：**「用户完全未配置文本模型」**在本项目中表现为 **`resolve_effective_text_service` 返回 `Err`**，调用方应在 **进入** `ensure_prompt_for_model` **之前**解析；**不要把「未配置」当成 `None` 传入压缩路径**（除非产品明确采用 §6.7 的 **Optional + 截断** 策略）。

### 6.6 超长 prompt + 无可用压缩用工：`ensure_prompt_for_model` 会不会 fallback？

**不会。** 本模块契约保持 **`text_service: &AiServiceConfig`**（或由编排层先 `resolve...?`）：  

- **需要压缩**（触发危险区或超 `l_max`）时，若调用方 **得不到**合法 `AiServiceConfig`，应 **直接 `Err`**，文案由编排层统一（可与现 `image_gen_prepare` 提示一致：引导用户配置文本服务商或缩短正文）。  
- **`ensure_prompt_for_model` 内部**不做「换本地启发式截断」「改用别的未选中模型」等隐藏 fallback（与 **AGENTS「禁止对用户未选择的接口做降级」** 一致）。

### 6.7 这是不是 Breaking？——按管线对照 **现状**

| 路径 | 现状（代码行为） | 迁移到「统一模块 + 需压缩则必须有文本服务」后 |
|------|------------------|-----------------------------------------------|
| **`image_gen_prepare`**（生图内嵌） | 已写明：**未配置文本服务且需要压缩 → `Err`**（见 `image_gen_prepare.rs` 内注释「未配置文本服务时返回错误」）。 | **等价**：不是新口径，只是把逻辑搬到 `generate_image` 编排 / `ensure_prompt_for_model`。 |
| **`cast_portrait` + `use_text_extract=false`（历史 Bug）** | 曾传 `None` → 超长即错。 | **修复方向**：压缩用工 **始终** `resolve...?`，与 extract 开关解耦；**不是**放宽为无配置也可发图。 |
| **`commands/image/commands/image_gen.rs`** | `resolve_effective_text_service(...).ok()` → `None` 时，超长仍走 `prepare` → **同样 Err**。 | **等价**。 |
| **`clips/commands/video_submit.rs`** | **`prompt_compressor`**：`FallbackToOriginal`；失败则 **`chars().take(max_chars)`** 硬截断（且 `max_chars = 4000` 与 **`model_capabilities` 中部分 `video_*` 的 800 等** 不一致）。 | **行为变更**：若改为「仅 `ensure_prompt_for_model` + 无静默截断」，则 **Clips 对用户而言更「硬」**——属于 **该产品路径上的 Breaking**，须在发版说明 / UI 提示中写明。 |

### 6.8 Clips / 可选产品策略：`PromptLengthPolicy`（避免 UX 断崖）

若产品希望 **保留「无文本服务也能尽量发出视频」**，应在 SPEC 层显式分叉，**禁止**与演员肖像路径混用同一套隐蔽逻辑：

| 策略 | 语义 | 典型用途 |
|------|------|----------|
| **`CompressRequired`** | 需要压缩时必须 **`resolve_effective_text_service` 成功**；否则 `Err`；LLM 两次失败 → `Err`。 | 生图主路径、质量优先。 |
| **`CompressPreferredTruncateToCap`** | 优先 **`ensure_prompt_for_model`**；若 **`resolve` 失败** 或 **压缩失败**，则 **按 `max_prompt_chars_for_kind(provider_kind)` 做 Unicode 安全截断**（可叠加 `warnings` / 任务详情），**禁止**静默改用未授权模型。 | Clips 等「宁可丢尾部描述也要出片」的场景；上限必须以 **能力表 `provider_kind`** 为准，废弃 Clips 内写死 `4000`。 |

默认推荐：**生图走 `CompressRequired`**；**Clips 若需平滑迁移先走 `CompressPreferredTruncateToCap`**，再在设置齐全后逐步收紧为 Required（产品决策）。

#### 7.1.1 Clips 视频：`ensure_prompt_for_model` 的 `provider_kind` 从哪来？（仓库现状 · 实施必读）

以下回答「§7.1 表里写视频通道，但 `video_submit.rs` 只有 `prompt_compressor`、没有 `provider_kind` 变量」的疑惑：**迁移后**长度与危险区必须以 **`model_capabilities`** 为准，键的来源如下。

**结论（单一来源）**

| 用途 | 字段 / 函数 | 说明 |
|------|-------------|------|
| **能力表键**（`max_prompt_chars_for_kind` / `prompt_threshold_ratios` / `ensure_prompt_for_model`） | **`AiServiceConfig.provider`** | Rust **`config::AiServiceConfig`** 只有 **`provider: Option<String>`**，**没有**单独的 `providerKind` 成员；JSON 与 TS **`AiServiceConfig.provider`** 对齐。 |

| **人读标签 / 日志** | **`ClipsGenerateVideoArgs.provider_label`** | 仅供 **`dev_log_final_prompt`** 等展示；**禁止**当作 **`provider_kind`** 去做字数上限。 |

**IPC 与调用链（锚点）**

- **`ClipsGenerateVideoArgs`**：`src-tauri/src/clips/commands/video.rs` — 含 **`video_service: AiServiceConfig`**、**`provider_label`**。
- **视频厂商分支**：`src-tauri/src/open_platform/video.rs` — **`VideoProviderKind::from_service(service)`** 读取 **`service.provider`**（经 `norm_provider_slot`），与 Clips 传入的 **`video_service`** 一致。
- **现状压缩（待替换）**：`src-tauri/src/clips/commands/video_submit.rs` — **`prompt_compressor`** + 写死 **`max_chars = 4000`**，**未**读 **`provider`**，与 **`max_prompt_chars_for_kind`**（如部分 **`video_*` 为 800）不一致**；迁入 **`ensure`** 后废止写死上限。

**前端 / 设置侧命名（为何界面叫 `providerKind`、包里叫 `provider`）**

- 账号 **`CapabilityBinding`** 等业务结构使用 **`providerKind`**（如 `ui/src/settings/appSettings.ts`）。
- 组装发往 Tauri 的 **`AiServiceConfig`** 时，通常写入 **`provider`** = 后端路由用的 id（与生图侧 **`provider: imgPick.backendId`** 同类）；视频常用 **`videoProfileBackendId(providerKind)`**（例如即梦 720P → **`volcengine_jimeng_t2v_v30_720p`**）。
- TS：**`AiServiceOverride`** 含 **`providerKind`**；**`AiServiceConfig`** 仅 **`provider`**（见 `ui/src/api/types.ts`）。

**推荐给 `ensure_prompt_for_model` 的拼接顺序（示意）**

1. `raw = video_service.provider.as_deref().unwrap_or("").trim()`
2. `pk = normalize_provider_kind(raw)`（再带入 **`check_length` / 压缩意图**）
3. **`provider_label` 不参与**上述步骤。

**`provider` 为空或未识别的边界**

- **`VideoProviderKind::from_service`** 在未知 **`provider`** 时落入 **OpenAPI 兼容**；**`max_prompt_chars_for_kind`** 对未单独声明的 kind 多为 **`0`**（表示本模块**不**声明硬上限）。
- **禁止**在无产品决策时继续沿用 Clips 旧 **`4000`**。
- 实施上优先：**缺失通道 id → `Err`**（要求 UI 必须带出有效视频配置）；若采用 **§6.8 `CompressPreferredTruncateToCap`**，须在任务 **`warnings` / 详情**中明示「未绑定 canonical 上限时的截断策略」。

### 7.2 生图：谁来负责 `to_natural_language_prompt` / passthrough？（权威）

**结论（推荐，项目最优解）**

| 层次 | 职责 |
|------|------|
| **公共 API（单一实现）** | 从 `open_platform/image.rs` **抽出**与当前完全等价的逻辑：**`normalize_image_prompt_for_dispatch(raw: &str) -> ImagePromptDispatchNormalized`**（类型定义见下 **§7.2.0**）。全仓 **只允许这一处**实现该组合语义，**禁止**管线复制粘贴 `image.rs` 里的 if 分支。 |
| **编排者（Orchestrator）** | **`open_platform::image::generate_image`**。函数体内：**①** `let norm = normalize_image_prompt_for_dispatch(params.prompt)` → **`params.prompt = norm.body`** → **②** **`enforce_no_watermark_constraint`**（与现状一致：**始终**执行）→ **③** **`if !norm.is_passthrough`**：`ensure_prompt_for_model` → `prepare_generate_image_request`（参考图裁剪等，**无** LLM 压缩）；**`else`**：**跳过** `ensure` **且跳过整段** `prepare`（与当前 ```696:704:src-tauri/src/open_platform/image.rs``` 一致）→ **④** HTTP。**管线调用方只传原始串**。 |
| **`ensure_prompt_for_model`（跨模态模块）** | **不**在内部解析 RAW / naturalize；仅消费 **`norm.body`**（见 §7.2.0）。 |
| **Passthrough** | 由 **`norm.is_passthrough == true`** 表示；**跳过** `ensure` 与 **整段** `prepare`（与现状一致）。若未来要求直通也限长，须改 **`ImagePromptDispatchNormalized`** 语义或增字段后再立项。 |

#### 7.2.0 `ImagePromptDispatchNormalized` 是什么？（决定分支的结构体）

**必须是带模式的结构化返回值**，不能只返回 `String`：否则 **`generate_image` 仍须在本函数内重复解析 `RAW_PROMPT_PASSTHROUGH_PREFIX`** 才能决定是否 **`ensure` / `prepare`**，违背「单一真相」。

**推荐 Rust 形状（可与枚举二选一）**

```rust
/// 与当前 `generate_image` 开头语义一致：`trim` → 可选剥离 RAW 直通前缀 → 要么 naturalize 要么保持剥离后正文。
pub struct ImagePromptDispatchNormalized {
    /// 写入 `GenerateImageParams.prompt` 的正文（已是「最终 naturalize 形态」或「直通形态」，见 `is_passthrough`）。
    pub body: String,
    /// `true`：输入以 `RAW_PROMPT_PASSTHROUGH_PREFIX` 开头且已剥离前缀 → **对应现状不做 `to_natural_language_prompt`**。
    pub is_passthrough: bool,
}
```

（可选）将 `is_passthrough: bool` 改为 **`enum ImagePromptDispatchMode { Passthrough, Naturalized }`**，语义等价，便于扩展第三种模式时再改名。

**与编排的对应关系（权威）**

| `is_passthrough` | `ensure_prompt_for_model` | `prepare_generate_image_request` |
|------------------|---------------------------|----------------------------------|
| **`false`** | **执行**（非空且超限时压缩） | **执行**（参考图张数裁剪、可灵文生图丢参考图告警等） |
| **`true`** | **跳过**（产品现状：直通不参与长度策略） | **整段跳过**（与仓库现状一致；直通路径 **不**跑参考图裁剪等 prepare 副作用——若未来要在直通下仍裁剪参考图，须单独立项改行为） |

**注意**：`normalize_image_prompt_for_dispatch` 的入参建议为 **`params.prompt` 经 `trim` 后的视图**（或函数内统一 `trim`），与现 `generate_image` 一致；**不要**要求调用方预先剥离 RAW 前缀。

#### 7.2.1 `to_natural_language_prompt` 是否幂等？会不会「管线先 normalize + `generate_image` 再 normalize」？

**结论：`prompt_natural_language::to_natural_language_prompt` 不是幂等函数。**

依据实现（`src-tauri/src/prompt_natural_language.rs`）：

- 对 **可解析的结构化稿**（标题行、`【】`、列表、`#` 等），输出通常会 **改写结构** 并套上固定前言，例如中文下前缀 **`请根据以下自然语言描述生成画面：`**（英文下为另一固定前缀）。
- 若把 **上述输出再次喂给** `to_natural_language_prompt`，解析路径会把整段当作 **新的正文行** 继续拼接，**极易再次包一层同类前缀或改变分句**，从而 **字数与语义轮廓都可能变化**。
- 仅当解析结果 **`clauses` 为空**时函数 **退回** `trim` 后的原文；这对「已是自然段、无结构化触发条件」的输入表现为 **近似不变**，但 **不能**据此宣称全局幂等——**只要第一次变换发生过，第二次就可能叠加变换**。

因此：

| 误区 | 正确约束 |
|------|----------|
| 「调用方先 naturalize 一次，`generate_image` 再 naturalize 一次，最多不变」 | **错误**：第二次可能 **重复套壳 / 变长**，且 **`ensure_prompt_for_model` 若在两次之间只执行一次** 会导致 **长度判定与最终 HTTP 正文不一致**。 |
| 「前提：所有调用点在 naturalize 之后先做 ensure，再进 `generate_image`」 | **与推荐编排冲突**：若 `generate_image` **仍内含** naturalize，则必须 **禁止**调用方提前 naturalize；**唯一允许的单次 naturalize** 应发生在 **`generate_image` 内的 `normalize_image_prompt_for_dispatch`**（见上表编排者）。 |
| **`ensure_prompt_for_model` 的输入** | **非 passthrough**：必须是 **`normalize` 之后、`enforce_no_watermark_constraint` 之后** 的 **`params.prompt`**（见 **§7.2.3**）。**不得**在「仅 naturalize」阶段就做字数就绪后又追加正向水印条款。**不得**假设调用方已 naturalize + `generate_image` 再 naturalize。 |

**推荐不变**：业务 **只传原始业务稿** → **`generate_image` 内**：**normalize → watermark →（非 passthrough）ensure → prepare**。**除非**未来引入显式 `skip_inner_normalize: bool` 并由审计保证不会双重调用，否则不要分叉。

**为何不采用「每个管线先 normalize 再 ensure」？**

- 若由各 `*_pipeline.rs` 先调一次公共 `normalize` 再 `ensure` 再调 `generate_image`，而 **`generate_image` 内部仍保留一遍 normalize**，则会出现 **双重规范化**（除非再引入 `skip_normalize` 标志，标志泛滥易错）。
- 若由各管线先 normalize 再 ensure，且 **`generate_image` 删除内部 normalize**，则 **每一个** direct `generate_image` 调用点都必须记得先 normalize，**遗漏即行为漂移**，耦合面反而更大。

因此：**规范化 + 长度就绪** 对生图应 **集中在 `generate_image` 入口编排**；公共函数仅解决「逻辑只维护一份」，**不负责**「谁调用」——**谁对外承诺最终 HTTP 正文，谁编排**。

#### 7.2.2 `generate_image` 如何传入 `db` / `job_id` / 压缩用工？方案 A vs **方案 B（选定）**

**现状**：`generate_image(kind, service, params, prep_text)` **仅有** `prep_text`，无 `db` / `job_id`，压缩过程无法稳定写入 **`ai_task::update_progress_merge`**（§8）。

| 方案 | 形态 | 优点 | 缺点 |
|------|------|------|------|
| **A：追加三个 `Option` 参数** | `..., db: Option<&DbState>, job_id: Option<&str>, text_service_for_compress: Option<&AiServiceConfig>` | 改动直观；无需新类型 | 签名冗长；**每增一项横切关注点就要改所有调用点顺序**；易把参数排错 |
| **B：`GenerateImagePromptContext<'_>`（选定）** | 单结构体聚合上述三字段（均为 `Option`） | **扩展面稳定**（后续加 `trace_id`、开关位等不改函数 arity）；调用处 **`GenerateImagePromptContext::none()`** 一眼可读；评审时「压缩上下文」边界清晰 | 多一个类型文件 / `impl` 块 |

**项目最优解：采用方案 B。** 方案 A 仅可作为短期过渡，**不作为**规格终点。

**推荐类型与签名（示意）**

```rust
/// 生图链路中「模型提示词就绪 + 任务进度」所需的横切上下文；与 `ImageProviderKind`、`GenerateImageParams` 正交。
/// 凡字段为 `None`：`ensure_prompt_for_model` **跳过**对应能力（如无 `db`/`job_id` 则不做进度合并；无 `text_service_for_compress` 且触发压缩则 **`Err`**，与 §6 一致）。
pub struct GenerateImagePromptContext<'a> {
    pub text_service_for_compress: Option<&'a AiServiceConfig>,
    pub db: Option<&'a DbState>,
    pub job_id: Option<&'a str>,
}

impl<'a> GenerateImagePromptContext<'a> {
    pub const fn none() -> Self {
        Self {
            text_service_for_compress: None,
            db: None,
            job_id: None,
        }
    }
}

pub async fn generate_image(
    kind: ImageProviderKind,
    service: &AiServiceConfig,
    mut params: GenerateImageParams,
    prompt_ctx: GenerateImagePromptContext<'_>,
) -> Result<GenerateImageOutput, String>
```

- **废除**最后一个位置的 **`prep_text`**：`text_service_for_compress` **完全取代**其语义（名称明示「仅用于压缩」，避免再与 `use_text_extract` 混淆）。
- **无任务 / 无进度场景**（如部分 IPC）：传入 **`GenerateImagePromptContext::none()`**，由 **`ensure_prompt_for_model`** 内部对 `job_id`/`db` 为 `None` 时跳过 `update_progress_merge`（见 §8）。
- **有任务的管线**：由 command / pipeline 从 `State` 取 `DbState`，传入 **`job_id` + `db` + `resolve_effective_text_service(...)?`** 填 ctx。

#### 7.2.3 `enforce_no_watermark_constraint` 与 `ensure_prompt_for_model` 的顺序（强制）

**问题**：若在 **`ensure_prompt_for_model` 已将正文压到 ≤ `l_max`** 之后，再执行 **`enforce_no_watermark_constraint` 往 `params.prompt` 追加**「不得出现水印…」等 **正向**句子，则 **`chars().count()` 可能再次超过 `l_max`**，违背压缩语义，甚至直接导致下游拒请求。

**结论（不可接受「ensure → 再正向叠水印」）**

| 顺序 | 判定 |
|------|------|
| **`normalize` → `enforce_no_watermark_constraint` → `ensure_prompt_for_model` → `prepare` → HTTP** | **选定**（与仓库 ```693:697:.\src-tauri\src\open_platform\image.rs``` **先于** `prepare` 调用一致；SPEC §7.2 编排者表亦采用此序）。字数校验与 LLM 压缩针对 **「即将参与长度约束的正文」**，已含 **可能需要追加的正向水印条款**。 |
| **`normalize` → `ensure` → `enforce_no_watermark`（正向追加）→ HTTP** | **禁止**：会把 **水印增量** 压在 **`l_max` 之外**。 |

**与 `negative_prompt` 分支的关系**：当 `model_capabilities::negative_prompt_caps_for_kind` 表明 **支持 `negative_prompt`** 时，`enforce_no_watermark_constraint` **优先把水印相关语义写入 `negative_prompt`**，**不一定**拉长 **`prompt`**。此时「水印在前、ensure 在后」仍安全且一致。**不支持 negative** 的通道才会 **改写正向 `prompt`**，顺序要求对此 **尤其关键**。

**直通（passthrough）**：现状仍 **先** `enforce_no_watermark_constraint` **再**决定是否进入 `prepare`；直通跳过 `ensure` 与整段 `prepare` 时，水印约束 **仍会**施加（与现网一致）。若直通正文也因水印追加而超长，属 **产品是否要限制直通长度** 的独立议题（当前 SPEC 不改为直通强制 ensure）。

**非生图链路（视频 / 文本 / TTS）**

- **没有**与 `generate_image` 共享的 naturalize 规则；各自在 **即将写入请求体的那个入口** 编排：**最终正文 → `ensure_prompt_for_model` → HTTP**。
- 亦 **不把** 视频文案塞进 `normalize_image_prompt_for_dispatch`。

### 7.3 `cast_portrait.rs` 文本服务

压缩用工：**在进入 `generate_image` / `ensure` 编排之前** `resolve_effective_text_service(...)?` **强制成功**（未配置则 **`Err`**，见 §6.5–§6.7）；**与 `use_text_extract` 无关**（extract 仅控制是否另走「视觉关键词提取」链路）。

## 8. AI 任务进度协议（与模态无关）

### 8.1 仓库现状：前端如何读 `lastPayload`

IPC / 列表类型见 `ui/src/api/types.ts`：`AiTaskListItem.lastPayload` 为 **`Record<string, unknown>`**，各界面按 **约定键名** 读取（camelCase）。

| 消费位置 | 路径 | 实际用到的键（与压缩相关） |
|----------|------|---------------------------|
| **任务页 · 阶段一行** | `ui/src/components/TasksTab.tsx` → **`payloadStageLine`** | **stage**、**phase**、**title**（三者非空则 `join(" · ")`）；可选 **elapsedMs**。**不读取 detail**。 |
| **演员 Tab · 进度文案** | `ui/src/features/character-tab/utils.ts` → **`formatCastStillProgressLine`** | 仅对白名单 **`phase`**（`prepare` / `extract` / `merge_dedupe` / `synthesize` / `image` / `persist`）映射 i18n；**其它 `phase`**（含 `prompt_validation`、`prompt_compression` 等）落入 **`return p.title?.trim() || …`**，即 **靠 `title` 展示人读文案**。 |
| **类型收窄（演员）** | `ui/src/features/character-tab/types.ts` → **`CastStillProgressPayload`** | 声明了 `stage` / `phase` / `title` 等；**未列出的键仍可出现在 JSON 中**（运行时存在），TS 不会自动提示而已。 |

结论：后端 **`update_progress_merge`** 只要保证 **`title`（及可选 `phase`）为人可读**，**无需**前端先发版即可在 **任务页阶段行** 与 **演员进度条** 看到压缩阶段（任务页会串上 `phase` 字符串；演员页未知 phase 时显示 **`title`**）。

## 11. 实施阶段清单

### 依赖与禁止的中间态（强制）

若 **Phase 2** 仅接入 **`ensure_prompt_for_model`**（新签名 / 编排），而 **`prepare_generate_image_request` 仍保留** `compress_prompt_for_image_cap`（现状见 `image_gen_prepare.rs`），则一段时间内存 **双重 LLM 压缩**：先 **`ensure`** 再 **`prepare`**，语义漂移、成本与延迟皆不可接受。

**项目裁定（二选一，但必须满足「无双重压缩」）**

| 策略 | 说明 |
|------|------|
| **A（推荐）** | **Phase 2 与「`image_gen_prepare` 去掉 LLM 长度压缩」同一 MR / 紧密连续提交**，视为 **原子交付**：合并后 **`generate_image` 内压缩唯一出口**为 **`ensure`**；**`prepare` 仅保留**参考图裁剪、通道告警等非字数逻辑。 |
| **B**（次选） | 若必须拆分提交：**可先**「`prepare` 内删除 LLM 压缩」**再**接 ensure；**禁止**先发 ensure 再事后删 `prepare` 压缩。**注意**：删除压缩而尚未接入 ensure 的窗口内，超长 prompt 可能 **直送厂商**，须 **同一发布列车 / 紧相邻合并** 或开关保护；默认仍优先 **策略 A**。 |

**`prompt_compressor.rs`**：仍由 **Clips** 等使用，**删除文件**须在 **Phase 3** 迁移完成后执行（见下 **Phase 4**），与上图原子化 **无关**。

## 13. 附录 B：`prompt_threshold_ratios`（危险区）填报规则与官方依据表

### 13.1 术语

| 术语 | 含义 |
|------|------|
| **`L_max`** | `max_prompt_chars_for_kind` 返回值（Unicode 标量计数，与仓库实现一致）。 |
| **`(r_warn, r_safe)`** | `prompt_threshold_ratios` 返回的两个比例；`L_warn = floor(L_max * r_warn)`，`L_safe = floor(L_max * r_safe)`，且 **`r_warn < r_safe`**。 |
| **危险区压缩** | `L_warn < n ≤ L_max` 时仍触发 LLM 压缩至 **`L_safe`**，用于规避「未顶满官方上限但已不稳定」的情况。 |
| **显式 `(None, None)`** | 官方（或当前可获得文档）**仅声明硬上限 + 截断/报错**，**未给出**可量化为比例的不稳定区间；**禁止**为生搬「全员危险区」而臆测 `r_warn/r_safe`。 |

### 13.2 何时允许写成非空 `(r_warn, r_safe)`（硬门槛）

满足 **下列之一** 方可把代码中的 `(None, None)` 改为 `Some`：

1. **官方数值型软区间**：文档明确写出「建议不超过 X 字」「超过 Y 字不稳定」等 **可换算为与 `L_max` 可比阈值** 的表述（须在表中粘贴 **原文摘录 + 文档版本日期**）。  
2. **项目观测备案**：与当前 **即梦 4.6** 同类——线上可复现的错误码/日志表明「接近上限即不稳定」，且仓库 Issue/工单 **`OBS-YYYYMMDD-xxx`** 中给出样本 `traceId`、请求时长、`provider_kind`、近似字数区间；比例变更须在 PR 中引用该工单。

**不允许**：仅凭主观经验、第三方聚合站点、或与当前接口版本未对齐的旧截图设定比例。

### 13.3 文本类 `text_*`（`L_max` 为上下文换算）

| 规则 |
|------|
| `text_deepseek_compat`、`text_volc_ark_compat`、`text_openai_compat`、`text_qwen`、`text_local_model` 等：**固定保持 `(None, None)`**。 |
| 该类 `L_max` 来自「上下文 token × 保守字符换算」，**不是**单一请求用户 prompt 的官方硬上限；**禁止**套用生图危险区比例。 |
