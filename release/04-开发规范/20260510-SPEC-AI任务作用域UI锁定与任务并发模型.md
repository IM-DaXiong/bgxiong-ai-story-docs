## 1. 大方向审核（是否符合原始要求）

| 原始要求 | 审核结论 | 说明 |
|----------|----------|------|
| 按任务 ID + 关联内容 ID，仅锁定「当下内容」 | **符合** | 以 `ai_tasks.id` 为任务实例键；以 `storyId` +（按 kind 的）节点 ID / payload 数组约定为内容键；UI **busy** 必须为「当前编辑上下文与某 running 任务相交」。 |
| 切换其他 ID 后同界面仍可操作 | **符合** | 相交判定假阴性不允许「误锁」；允许假阳性仅限 **明确的全 Story 级任务**（见 §6.3）。 |
| 高内聚、低耦合独立模块 | **符合** | 解析与相交集中在 `ui/src/domain/aiTaskContentScope/*`；React 层禁止手写散落 `find(running)`。 |
| 不兜底、不兼容 | **符合** | strict 解析：键缺失 / 类型错误 / trim 后空串 ⇒ **该任务不参与锁定**；禁止多键猜测（如 `chapter_id` / `chapterNodeId` 混用）。可选 DEV 日志便于暴露契约漂移（§8.3）。 |
| 说明是否任务池、是否阻塞 | **符合** | 见 §3；前端不得用单一全局 busy 推断。 |

**偏差澄清（避免误解）**  

1. **`polledRunningStoryChapters` / `polledRunningCastStill`**：可保留为「兼容旧 Props 的便捷导出」，但语义必须改为 **「仅在缺少 `storyAiTasks` 全量列表时的退路」**——**不推荐**；落地时应倾向 **废弃** 或在实现内部改为调用统一 `findRunningTaskForUiContext`。  
2. **副作用型 `some(running)`**：部分 hook 用「任意 `role_portrait` running」触发 **刷新列表**，这与 **表单禁用** 不同；§5 表格中区分 **Lock（禁用）** vs **Refresh（刷新触发）**。

## 2. 背景与已核实根因（摘要）

### 2.1 典型缺陷

- **`story_chapters`**：`useAiTaskPolling` 取「全局第一条 running」，未过滤 `task.storyId === activeStory.id`（`useAiTaskPolling.ts` `polledRunningStoryChapters`）。  
- **本地 `aiGenerating`**：`useAiGenerateChapters` 使用布尔值，未绑定发起时的 `storyId`。  
- **`chapter_scenes_plan`**：`useChapterScenesPlan` / `useSceneChapterBoard` 中 `runningChapterBoard = storyAiTasks.find(isChapterScenesPlanKind && running)`，**未**要求 `task.storyId === story.id` 且 **未**要求 `lastPayload.chapterNodeId === activeChapter.id`（或当前 `chapter.id`）。切换剧集或故事时仍会 **boardBusy**。  
- **`upsert_story_roles_batched`**：`RoleTabImpl.tsx` 中 `storyGenTaskRunning` 未过滤 `job.storyId === story.id`，会阻断其它故事的「从故事生成角色」。  
- **`useStoryboardQualityGate`**：全局 `find` running 的 `chapter_scenes_plan` / `scene_shots_plan`，未与当前画布三元组对齐。

### 2.2 已有正确范式（应对齐而非推翻）

- **`cast_portrait_still`**：`useCastPortraitStillPipeline` — `actorNodeId` + 选中演员 ID。  
- **`scene_concept_image`（场景资产）**：`useSceneAssetConceptGeneration` — `sceneNodeId` + `activeAsset.id`。  
- **`portrait_extracted_hints`**：`CharacterTabScreen` — `actorNodeId` + `selected.id`。

## 3. 任务并发模型（产品口径）

### 3.1 `ai_tasks`（SQLite）

- 多行并存；**无**「全局最多一条 running」约束。  
- `story_id`、`kind`、`state`、`last_payload` 为 UI 判定主输入。

### 3.2 `ai_queue`（可选执行路径）

- 默认 **`SerialStrategy` + `max_concurrency = 1`**（`scheduler.rs`）：**队列任务串行执行**，可多任务排队。  

### 3.3 直连 Tauri Command

- 例如 `generate_story_chapters`：插入 `ai_tasks` 后直接跑管线；前端常 `await invoke`。  
- **与队列并行关系**：不由此 SPEC 统一规定；前端 **禁止** 用「是否存在任意 running」代替「是否与当前上下文相交」。

## 4. 目标与非目标

### 4.1 目标（Must）

1. **统一内容真理来源**：凡依赖「任务是否与某段内容相关」的 **UI 锁定** 或 **业务判断**（拦截操作、合并刷新、质量门、冲突提示等），均应可表述为对 **`AiTaskListItem` 列表** 与 **`UiEditContext`（内容锚点）** 的相交查询（§8）。  
2. **表单禁用 / 主按钮 disabled** 为相交查询的典型用法：`exists running task T` 与锚点相交（often `findRunningTasksForUiContext` 非空）。  
3. **本地进行中**（未收到 finish）与 **DB `running`** 使用 **同一套锚点维度**（§7、§9）；本地状态 machine **不得**另起一套 ID 语义。  
4. 新增 kind：先改 **§6 登记表** + `parse…` + 调用方构造锚点；禁止先写散落 `find`。  

### 4.2 非目标（Won’t / 另立项）

- 不改「用户显式选择的模型 / 服务商」规则。  
- 不强制所有管线迁移 `ai_queue`。  
- **本期不强制** Rust DTO 新增 `scope` 列/字段；若后续要做，须离线迁移与单独批次（v1 文档 P2）。  

### 4.3 双用途定位：UI 锁定 **与** 业务判断（v3）

本模块的 **单一职责** 是：把 `AiTaskListItem` **无误地映射**为规范化的 **内容作用域**，并在给定 **内容锚点** 下回答 **集合意义上的相交问题**（哪些任务与当前上下文有关）。  

| 能力 | 是否属于本模块 | 说明 |
|------|----------------|------|
| `parse…` / `intersects…` / `find…` 纯函数 | **是（高内聚）** | 无 React、无路由、无 Toast；仅依赖 DTO 与 kind 登记表。 |
| `disabled={…}`、`interactionLocked` | **否（调用方）** | 业务层：`busy = findRunningTasksForUiContext(…).length > 0` 或与本地 invoke 状态组合。 |
| 「是否允许删除节点」「是否拦截导航」「是否自动刷新列表」 | **否（调用方策略）** | 使用 **同一套相交结果** 或 §8.6 的扩展查询；**禁止**把产品句式写进 domain。 |
| 新 kind / 新 payload 键 | **是（扩展点）** | 只改登记表 + `parse` 分支 + 测试；调用方无感升级相交语义。 |

**命名说明**：文中 `UiEditContext` 表示「当前业务所关心的内容锚点」，**不限于 UI**。实现时可选导出别名 `export type ContentAnchor = UiEditContext`（同义），便于在业务服务、hook、路由守卫中阅读。

**能否做到「高内聚、低耦合、可扩展」？——能**，条件是严守边界：

1. **高内聚**：所有「kind → payload 键 → `ParsedRunningTaskScope`」与「锚点 ↔ scope 相交」只存在于 `aiTaskContentScope/`。  
2. **低耦合**：domain **不** import 组件、**不** import `api.invoke`；业务代码只依赖公开 API。  
3. **可扩展**：新增场景 = 新增锚点 variant **或** 新增 kind 行 + 解析分支；相交表增量一行（§8.2）；必要时增加 §8.6 的状态过滤，而 **不** 复制粘贴 `find(running)`。

### 4.4 性能原则：复杂业务与高频计算优先 Rust（v5）

**产品级取向**：凡是 **计算量大**、**调用极频**、或 **牵涉复杂不变式与持久化事务** 的逻辑，优先放在 **`src-tauri`（Rust）** 执行；前端（TS/React）保持 **薄编排**：参数组装、`invoke`、展示状态。

与本 SPEC 相关的分工建议：

| 类别 | 倾向 | 说明 |
|------|------|------|
| AI 管线、队列调度、DB 读写、`ai_tasks` 写入与合并进度 | **永远在 Rust** | 已是现状。 |
| 重聚合 / 大批量任务扫描（例如单次上万条、或对同一列表每秒多次多维过滤） | **Rust** | 提供单一 Tauri command（或现有 `list_ai_tasks` 的扩展参数），**一次 IPC** 返回「与锚点相交的任务子集 / digest」，避免 WebView 内重复全量 JSON 解析与遍历。 |
| 当前规模：`list_all_ai_tasks` 限幅约数百条、数秒级轮询、`parse + intersect` 纯函数 | **TS domain 可接受** | 复杂度 \(O(n \cdot k)\)，\(n\) 为任务条数、\(k\) 为 kind 分支常量；**不必为性能先行搬到 Rust**；以实测为准。 |
| 高频路径禁忌 | **前后端共同遵守** | **禁止**在 `requestAnimationFrame` / 输入防抖内热路径上 **`invoke` 查库**；相交判定应在 **任务列表 digest 未变时短路**（沿用现有 digest 思路）。 |

**若未来迁至 Rust**：契约必须与 §6～§8 **同源**——推荐 **Rust 实现为权威解析 + 相交**，TS 仅保留类型与薄封装（或可 codegen）；避免 Rust / TS 两套规则漂移。

## 5. 全仓盘点：Lock vs Refresh（落地改哪里）

**图例**  

- **Lock**：直接影响 `disabled` / `interactionLocked` / `busy`。  
- **Refresh**：任务结束触发刷新；应优先按 **`storyId`（及必要时节点的 ID）** 过滤，避免无关 Tab 抖动（可做 P2 优化）。  

| 文件 | 现状问题 | 类型 | 落地动作 |
|------|----------|------|----------|
| `useAiTaskPolling.ts` | `polledRunningStoryChapters` / `polledRunningCastStill` 全局 `find` | Lock 数据源 | 改为按调用方传入的 context 选取，或标记 deprecated，由 Tab 使用 domain API |
| `StoryTab.tsx` + `useAiGenerateChapters.ts` | 远程未按 story；本地布尔未绑 story | Lock | P0：`UiEditContextStoryRoot` + `invokingStoryIdRef` |
| `useChapterScenesPlan.tsx` | `runningChapterBoard` / `boardBusy` 全局 | Lock | P0：`storyId` + `chapterNodeId`；本地 `boardGenerating` 绑 `chapterNodeId` |
| `useSceneChapterBoard.ts` | 同上 | Lock | P0：与上一行同构 |
| `useStoryboardQualityGate.ts` | 全局 running | Lock/展示 | P1：传入 `storyId` + `chapterNodeId` + `sceneNodeId`（与画布选中一致）再取任务 |
| `RoleTabImpl.tsx` | `upsert_story_roles_batched` 未过滤 `storyId` | Lock | P0：`job.storyId === story?.id` |
| `useCastPortraitStillPipeline.ts` | 逻辑已合理；依赖全局 `polledRunningCastStill` 时「双 actor 同跑」可能取错一条 | Lock 边缘 | P1：`findRunningTaskForUiContext` 取代「先全局 find 再比 actor」 |
| `useSceneAssetConceptGeneration.ts` | 已按 asset | Lock | P1：迁入 domain（减少重复） |
| `CharacterTabScreen.tsx` | `portrait_extracted_hints` 已按 actor | Lock | P1：迁入 domain |
| `useStoryRoles.ts` | 任意 `role_portrait` running 触发刷新 | Refresh | P2：`job.storyId === activeStory.id` 再触发 |
| `useRolePortraitWorkspace.tsx` | 任意 `role_portrait` running 触发刷新 | Refresh | P2：同上或按 `roleNodeId` |
| `SceneTabMainLegacyImpl.tsx` | 场次概念图：部分逻辑已按 `sceneNodeId` | Lock | P1：核对与 domain 一致 |
| `useChapterBatchAllChaptersScenes.ts` | 已 `j.storyId === storyId` | Lock | 保持；批量相交规则见 §6.3 |

## 6. `kind` 登记表（strict 契约）

### 6.1 解析总则

- **行级 `task.storyId`**：一律参与；与 UI 的 `context.storyId` 不等 ⇒ **不相交**。  
- **Payload**：一律读 **`task.lastPayload`**（TS：`AiTaskListItem.lastPayload`），键名 **camelCase**（与后端合并进度一致）。  
- **字符串字段**：`typeof === "string"` 且 `trim()` 非空；否则 **解析失败**。  
- **数组字段**：`Array.isArray` 且每项 `string` trim 非空；否则 **解析失败**。  

### 6.2 单锚点 / 单实体任务

| kind | Lock 级别 | 解析所需 payload 键（含行级 storyId） | 备注 |
|------|-----------|----------------------------------------|------|
| `story_chapters` | Story | 仅需行级 `storyId` | 不读 payload |
| `sync_story_roles` | Story | 仅需行级 `storyId` | |
| `upsert_story_roles` | Story | 仅需行级 `storyId` | |
| `upsert_story_roles_batched` | Story | 仅需行级 `storyId` | |
| `chapter_scenes_plan` | Chapter | `chapterNodeId` | |
| `scene_shots_plan` | Scene | `chapterNodeId` + `sceneNodeId` | 缺一即失败 |
| `segment_storyboard_image` | Segment | `chapterNodeId` + `sceneNodeId` + `segmentNodeId` | |
| `scene_concept_image` | Scene（资产与场次共用 payload 键） | `sceneNodeId` | UI 用当前资产/场次 ID 对齐 |
| `cast_portrait_still` | Actor | `actorNodeId` | |
| `actor_portrait` | Actor | `actorNodeId` | 若当前后端未写键 ⇒ 解析失败 ⇒ 不锁（暴露契约问题） |
| `portrait_extracted_hints` | Actor | `actorNodeId` | |
| `role_portrait` | Role | `roleNodeId` | `chapterNodeId` 若存在则参与 **细化相交**（§6.4） |
| `role_portrait_prompt_ai` | Role / Story | **本期**：若仅有行级 storyId，按 **Story** 锁「该故事角色 Tab 相关批量入口」；若 payload 含 `roleNodeId` 则细化 | 以后端实际 `mark_submitted` 为准，缺键则不锁 |
| `role_portrait_prompt_ai_chapter` | Role+Chapter | `roleNodeId` + `chapterNodeId` | 缺一即失败 |
| `optimize_chapter_prompt` | Chapter | `chapterNodeId` | 若无则失败 |
| `optimize_storyboard_shot_prompt` | Segment | `chapterNodeId` + `sceneNodeId` + `segmentNodeId` | 缺一即失败 |
| `settings_model_validate` | **不参与 Lock** | — | 设置页校验，不禁用故事表单 |

### 6.3 批量 / 父任务（chapterNodeIds）

以下 kind 在 running 时，除 **行级 `storyId` 必须匹配** 外，还需满足 **章节集合相交**（strict：`chapterNodeIds` 为 string[]）：

| kind | 相交规则 |
|------|----------|
| `story_all_chapters_scenes_batch` | `chapterNodeIds.includes(ui.chapterNodeId)` |
| `story_scenes_shots_plan_batch` | 同上 |
| `chapter_scenes_shots_plan_batch` | 同上（且通常 story 已匹配） |

**UI 仅有 Story 根上下文、无 `chapterNodeId` 时**：是否视为与批量任务相交 → **产品默认：相交**（禁用「再开一批」类按钮）；须在构造 `UiEditContext` 时显式使用 `story_root_batch_conflict` 变体（§7.1）。

### 6.4 `role_portrait` 细化规则

- 若 payload **无** `chapterNodeId`：`UiEditContextRole(roleNodeId)` 相交 ⇔ 任务解析出同一 `roleNodeId`。  
- 若 payload **有** `chapterNodeId`：`UiEditContextRoleChapter(storyId, roleNodeId, chapterNodeId)` 须 **三者全匹配** 才相交；否则不相交（避免「剧集 A 定妆锁了剧集 B 同一角色节点」——若业务需要全局锁角色，再单独开 SPEC）。

  domain: "ui";
  variant: "segment";
  storyId: string;
  chapterNodeId: string;
  sceneNodeId: string;

};

/** 演员 */
export type UiEditContextActor = {
  domain: "ui";
  variant: "actor";

export type UiEditContext =
  | UiEditContextStoryRoot
  | UiEditContextStoryBatchGate
  | UiEditContextChapter
  | UiEditContextScene
  | UiEditContextSegment

      kind: string;

## 8. 算法与 API 规格

### 8.1 `parseRunningTaskToScope(task: AiTaskListItem): ParsedRunningTaskScope | null`

1. 若 `task.state !== "running"` ⇒ `null`。  
2. 按 §6 表查 `task.kind`；未登记 kind ⇒ `null`（或 DEV warn）。  
3. 校验 `task.storyId` 非空 trim。  
4. 按 kind 读 payload；失败 ⇒ `null`。  

### 8.2 `intersectsUiContext(ctx: UiEditContext, scope: ParsedRunningTaskScope): boolean`

**前置**：若 `ctx.storyId !== scope.storyId` ⇒ `false`。

**语义拆分（避免「一批任务锁死整个故事文案」）**

- **`variant: "story_root"`**：仅用于「故事级流水线」占用的控件（典型：`story_chapters`、故事级 `sync/upsert_story_roles*`）。  
  - 与 **`ParsedRunningTaskScope.variant === "story_root"`**（由 §6.2 表中「仅需行级 storyId」之 kind 解析而来）相交。  
  - **不与** `chapter_batch` 相交——批量场次进行中时，**允许**编辑故事名称/简介等（除非产品日后另行规定）。
- **`variant: "story_batch_gate"`**：用于「再开一批 / 重复批量入口」等按钮互斥。  
  - 与 **`chapter_batch`**（§6.3）且同 `storyId` **相交**。  

**相交表（在 storyId 已相等前提下）**

| `UiEditContext.variant` | 与 `ParsedRunningTaskScope` 相交条件 |
|-------------------------|--------------------------------------|
| `story_root` | `scope.variant === "story_root"` |
| `story_batch_gate` | `scope.variant === "chapter_batch"` |
| `chapter` | `scope.variant === "chapter"` 且 `chapterNodeId` 相等；**或** `scope.variant === "chapter_batch"` 且 `chapterNodeIds.includes(ctx.chapterNodeId)` |
| `scene` | `scope.variant === "scene"` 且 `chapterNodeId`、`sceneNodeId` 全相等 |
| `segment` | `scope.variant === "segment"` 且三章一节 ID 全相等 |
| `actor` | `scope.variant === "actor"` 且 `actorNodeId` 相等 |
| `role` | `scope.variant === "role"` 且 `roleNodeId` 相等；**若** `ctx.chapterNodeId` 与 `scope.chapterNodeId` 两侧任一非空，则必须 **字符串相等**（含「仅一侧有章节锚点」视为不相交，强制后端补齐契约） |

### 8.3 DEV 可观测性（推荐）

- 首次 `parseRunningTaskToScope` 返回 `null` 且 `state===running` 时：`logWarn("AI_TASK_SCOPE", "PARSE_SKIP", { taskId, kind })`（**禁止**打印 token）。  
- 生产环境可降级为仅计数或关闭。  

### 8.4 选取展示用任务（进度文案）

```ts
export function findRunningTasksForUiContext(
  tasks: AiTaskListItem[],
  ctx: UiEditContext,
): AiTaskListItem[]
```

1. 过滤 `state === "running"`。  
2. `parseRunningTaskToScope` 非 null 且 `intersectsUiContext`。  
3. 排序：`updatedAtMs` **降序**（最新进度优先）。  

UI 若只需一条：取 `[0]`。

### 8.6 扩展 API（业务判断用，仍保持低耦合）

下列 API **可选实现**，与 §8.1～§8.4 并列导出；业务层按需引用，避免在 feature 内重复解析 payload。

| API | 用途 | 说明 |
|-----|------|------|
| `parseTaskToScope(task)` | 不限 `state` 的解析 | 与 §8.1 相同的 payload 规则，但 **不因 `state !== running` 而返回 null**；用于「历史上是否有过失败落在该章节」等（若仅需 running，继续用 §8.1）。 |
| `findTasksForUiContext(tasks, ctx, opts)` | 通用过滤 | `opts.states?: Set<string>`（如 `running` + `submitted`）；默认等价于 §8.4 仅 `running`。 |
| `taskIntersectUiContext(task, ctx, opts)` | 单条判断 | `parse`（尊重 opts 是否要求 running）+ `intersectsUiContext`。 |

**约束**：  

- **相交几何**仍只由 §8.2 决定；**不允许**在业务文件手写 second copy。  
- **`opts.states`** 扩展时 **不改变** payload 解析形状；仅过滤任务行。  
- **产品策略**（例如：相交时 `dialog.confirm` 还是静默禁止）留在 **feature / hook**，domain 只返回布尔或任务列表。

**反模式**：在 `services/` 再实现一套「类似 intersect 但不读 §6 表」——禁止。

## 14. 全仓 AI 任务 kind 枚举 + 灵活扩展（注册表 vs 注入）

### 14.1 要不要做「全仓统计枚举」？

**要。** 用途不是运行时去「扫项目」，而是维护 **单一真相来源（SSOT）**，与后端 `ai_task::insert_running`、队列 `TaskType`、迁移脚本保持同构。

| 做法 | 说明 |
|------|------|
| **文档表 §6** | 给人读的契约；**必须与代码 registry 同步修改**。 |
| **前端 registry**（推荐） | `parse` 实现只认 registry 中登记的 `kind`；未登记且 `state===running` → §8.3 DEV 告警（可选）。 |
| **定期审计命令** | 例如仓库根：`rg "insert_running\\(" src-tauri -g"*.rs"`；新增/删除 kind 时 diff 对照 `ui/src/domain/aiTaskContentScope/**` 与 `ui/src/domain/aiTaskKinds.ts`。 |

**原则**：枚举是为 **防止遗漏解析策略**，不是为在业务里写巨型 `switch(kind)`。

### 14.2 「注入式」设计要不要上？

**不建议**把解析器交给业务层「依赖注入」（例如在 Props 里传 `parseTask?: …`）。原因：解析规则分散、难 code review、易违背 §13「禁止散落 find」的精神。

**推荐形态（足够灵活 + 高内聚）**：

1. **内向注册表（Registry）**  
   - 例如 `SCOPE_PARSER_BY_KIND: Readonly<Record<string, ScopeParseFn>>` 或由 **`kind` 常量数组**驱动构建的只读 Map。  
   - **新增 kind**：只改 domain 内 **一处注册** + §6 一行 + 测试；业务代码零改（除非新锚点类型要传新的 `UiEditContext`）。

2. **策略对象（可选）**  
   - 对少数复杂 kind（批量父任务、`role_portrait` 章节细化），可用 `{ parsePayload, variant }` 小对象，仍挂在 **同一 registry**，不泄漏到 feature。

3. **仅测试用的「注入」**  
   - Vitest 可对 registry 做 **`withScopedRegistryOverride(() => …)`** 类 helper，或导入内部 `registerParserForTest`（不导出给生产 bundle）。  
   - **禁止**：生产路径 `mergeExternalParsers(userPlugins)`——违背「不兜底、可审计」。

### 14.3 与「低耦合」的关系

- **业务 / UI**：只依赖 **公开 API**（`findTasksForUiContext`、`intersectsUiContext`、锚点构造工厂函数）。  
- **domain**：内聚 **枚举 + 解析 + 相交**；Rust 侧 kind 常量（`ai_task_kinds.rs` 等）与 TS `aiTaskKinds.ts` 已在仓库存在，**registry 应引用这些常量**而非魔法字符串。

### 14.4 权威快照说明（避免文档与代码漂移）

本节 **不** 罗列完整 kind 清单（易陈旧）。**权威集合**以：

- `src-tauri` 内所有 `insert_running` 调用点、  
- `src-tauri/src/ai_queue/types.rs` 等队列映射、  
- `ui/src/domain/aiTaskKinds.ts`  

的合并为准；落地新增一条 **可选** 门禁脚本（非本文强制）：比对「Rust 中出现的 kind 字面量」与「frontend registry keys」差集。
