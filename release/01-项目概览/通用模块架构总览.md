# 全仓通用模块架构总览

**版本**：v0.2.719 | **统计日期**：2026-07-17

---

## 前言

本文档梳理了比格熊数字导演工作站项目中 **跨模块复用的通用基础设施**。这些模块不隶属于任何一个业务功能（故事、角色、分镜等），而是被所有业务模块共同依赖的"地基"。它们的设计遵循统一规范：**高内聚、低耦合、单一数据源、前后端职责分明**。

## 第一部分：UI 基础设施

### 1. 无限画布引擎（Infinite Canvas）

**规模**：~374 文件 / ~51,500 行（Rust 2,773 + TypeScript 48,509 + CSS 218）

画布系统是整个应用的 **核心交互空间**，承载了分镜编排、片段编辑、剪辑预览、角色卡片等所有需要空间布局的界面。它被设计为一个 **不关心业务内容、只负责空间管理** 的渲染内核。

#### 架构分层

```
┌─────────────────────────────────────────────┐
│ L4  业务宿主 (Consumer)                      │
│     分镜画布 · 片段画布 · 剪辑画布 · 角色卡片  │
├─────────────────────────────────────────────┤
│ L3  渲染外壳 (Render Shell)                  │
│     MasonryOsDropCanvasShell               │
│     CanvasNodeShell · CanvasEdgeLayer       │
├─────────────────────────────────────────────┤
│ L2  内核引擎 (Engine Core)                  │
│     视口裁切 · 拖拽状态机 · 缩放平移          │
│     选中管理 · 双击处理 · 空间模型           │
├─────────────────────────────────────────────┤
│ L1  布局引擎 (Layout Engine)                │
│     Masonry 瀑布流布局 · 拖拽窗口化           │
│     瓦片摆放策略 · 占位符生成                │
├─────────────────────────────────────────────┤
│ L0  基础设施 (Infrastructure)               │
│     四叉树空间索引 · DOM 事件归一化           │
│     几何工具库 · 撤销/重做快照               │
└─────────────────────────────────────────────┘
```

#### 八大设计模式

| 模式 | 说明 | 价值 |
|------|------|------|
| **渲染属性插件** | `InfiniteCanvas` 是无渲染内核，通过 `renderNode`/`renderEdge` 回调注入内容，画布本身不知道它渲染的是什么 | 一套画布引擎服务所有业务场景 |
| **四叉树视口裁切** | 仅渲染当前视口内的节点，配合四叉树空间索引实现 O(n log n) 裁切 | 千级节点不卡顿 |
| **分层拖拽窗口化** | 拖拽时仅完整挂载参与者+邻居，其余渲染为占位符 | 拖拽帧率稳定 |
| **Masonry 瀑布流** | `useMasonryCanvasLayout`（980 行）计算 bin-packing 流式布局 | 自动排版省去手动摆位 |
| **LOD 多级预览** | 前端按屏幕像素决定用缩略图还是原图；Rust 后端探针式生成 WebP 缩略图并缓存 | 画布上百张图也不卡 |
| **端口布局管线** | Rust 纯函数管线：sort → compact → allocate → derive，前端只消费结果 | 复杂布局计算放 Rust，前端零负担 |
| **快照撤销/重做** | 每次变更前保存状态快照，撤销时恢复 | 任何画布操作可回退 |
| **事件绑定器** | DOM 事件（滚轮/触摸/鼠标）经 `canvasRootListenerBinder` 归一化为类型化动作 | 一处绑定，全局消费 |
| **节点编组系统** | 画布节点可创建/解散/增删成员的编组框，支持幽灵端口扇出、共享端口折叠、连线手势、框选快速编组（Ctrl+G） | 复杂拓扑的节点组织与批量连线不再依赖手动逐个操作 |

#### 节点编组系统（Segment Canvas Group）

**规模**：~40 文件 / ~2,800 行（TypeScript）

编组系统是片段画布在 v0.2.719 引入的节点组织能力，将多个节点封装为一个可统一操作的编组单元。

##### 架构分层

```
┌─────────────────────────────────────────────┐
│ 渲染层 (Render)                              │
│   SegmentCanvasGroupFrameRenderer           │
│   GroupFrameColorPicker（8 色可定制）        │
│   SelectionBoundsChrome（多选虚线边框）       │
├─────────────────────────────────────────────┤
│ 交互层 (Interaction)                         │
│   useSegmentCanvasGroupActions              │
│   useSegmentLinkGesture（编组连线手势）       │
│   useSegmentCanvasTransitionLinking          │
├─────────────────────────────────────────────┤
│ 域逻辑层 (Domain)                            │
│   commitCreateGroup / commitUngroup          │
│   commitAddMember / commitRemoveMember       │
│   commitQuickGroupAndLink（框选快速编组）      │
│   commitResizeGroupFrame（编组框伸缩）        │
│   commitSetGroupFrameColor（颜色自定义）       │
├─────────────────────────────────────────────┤
│ 端口编排层 (Port Orchestration)              │
│   planCollapseSharedPortsAmongMembers        │
│   planReassignExclusivePorts                 │
│   syncMemberIntoGroupFanouts                 │
│   projectPortLayoutEdges / projectConsumable  │
│   reconcileGroupMembershipAfterPositionsCommit│
└─────────────────────────────────────────────┘
```

##### 核心设计

- **幽灵端口扇出**：成员入组后共享端口自动折叠为编组级单一端口，独立端口重分配到编组框，入组自动接入视频消费面
- **框选快速编组**：框选多个节点后按 `Ctrl+G` 一键创建编组并自动连线到消费面
- **拖拽调和**：拖拽节点进出编组区域后自动更新成员归属（`resolveGroupMembershipAfterDrag`）
- **编组连线**：编组框作为连线源/目标，支持从编组拖线到其他节点或画布外消费面
- **ID 方案**：编组节点使用 `group:` 前缀 ID，与普通节点命名空间隔离

#### 服务对象

分镜画布、片段画布、剪辑画布、角色卡片廊、场景概念图、参考图选择器、工作流图片库、分镜历史弹窗。

### 2. 通用 UI 组件库（Common Components）

**规模**：45 文件 / ~2,779 行

位于 `ui/src/components/common/`，是所有业务组件的"零件箱"。提供按钮、面板、弹窗、右键菜单、表单控件、列表项、分隔条等基础 UI 单元。

#### 子模块一览

| 子目录 | 文件数 | 核心输出 |
|--------|--------|----------|
| `button/` | 2 | `Btn`（支持 6 种变体：primary/secondary/danger/ghost/accent/ai） |
| `overlay/` | 9 | `Modal`（动画退出）、`ContextMenuShell`（位置钳制） |
| `form/` | 15 | `FormRow`、`RadioGroup`、`CheckboxField`、`useWorkbenchChoiceState` |
| `layout/` | 4 | `Panel`（可折叠区域）、`Splitter`（可拖拽分割条） |
| `feedback/` | 3 | `Toast`、`Tag`、`LightweightLoadingOverlay` |
| `cards/` | 1 | `Card`、`CardGrid` |
| `sequence-index/` | 6 | `SequenceIndexPopover`（序号编辑唯一壳层） |
| `list/` | 1 | `ListItem` |
| `utilities/` | 1 | `EmptyHint`、`SectionHeader` |

#### 核心设计原则

- **统一入口**：`import { Btn, Panel, Modal, Toast } from "../../components/common"` 一行导入所有组件
- **变体驱动**：按钮用 `variant` 枚举控制颜色语义（`ai`=紫色/AI操作，`primary`=蓝色/保存打开），禁止散落各处硬编码颜色
- **排版 SSOT**：所有组件字号使用 `typographyRefs` 引用，禁止裸 `fontSize: N`
- **`forwardRef`**：所有交互组件支持 ref 转发

### 3. 国际化系统（i18n）

**规模**：4 文件 / ~13,265 行

#### 架构

```
Locale 类型定义 (types.ts, 3,361 行)
    │
    ├──► zh-CN.ts (3,734 行) ── 完整的中文翻译对象
    │
    └──► en.ts (3,788 行) ── 完整的英文翻译对象
         │
         ▼
    React Context (index.ts, 40 行)
         │
         ▼
    useI18n() Hook ──► 任何组件调用 useI18n().story.title 等
```

#### 设计特点

- **类型安全的翻译**：`Locale` 接口定义了所有可翻译字符串的嵌套结构（`auth.loginTitle`、`storyboard.shotNumber` 等），两个语言文件编译时自动校验完整性
- **双层持久化**：语言选择写入 `localStorage` + 用户偏好（`applyPreferencesPatch`）
- **无运行时开销**：直接对象属性访问，无需 key 查找

### 4. 排版系统（Typography SSOT）

**规模**：~340 行（TS + CSS + 合规脚本）

#### 架构

```
CSS 变量 (:root)                    ← 唯一的像素值定义处
  --text-2xs: 11px
  --text-xs:  12px
  --text-sm:  13px
  --text-md:  14px
  --text-lg:  15px
  --text-xl:  16px
  --text-2xl: 18px
  --text-3xl: 22px
        │
        ├──► typographyRefs (TS)     ← UI 组件引用："var(--text-sm)"
        │
        ├──► typographyScreenPx (TS) ← 画布 Canvas 2D 渲染用数值
        │
        └──► 契约测试                ← 运行时解析 CSS 校验两端一致
```

#### 合规门禁（`check-typography-ssot.ps1`）

- 禁止 TS/TSX 中裸写 `fontSize: N` 数值
- 禁止 CSS 中 `font-size: Npx`（`:root` 外）
- 禁止 `var(--text-*, Npx)` 回退反模式
- 禁止画布 `SCREEN_PX` 常量出现在 `typographyScreenPx.ts` 之外

### 5. 主题系统（Theme System）

**规模**：~904 行（TS + CSS + 合规脚本）

#### 架构

```
CSS 层                            React 层
:root (深色默认)                  ThemeProvider (Context + localStorage)
[data-theme="light"]              ThemeSwitcher (四选一 radio 组)
[data-theme="sakura"]             themeEarlyHydrate (防 FOUC)
[data-theme="ocean"]
        │                              │
        └── cssVarRefs.ts ◄────────────┘
            (TS 引用代理：--primary → cssVarRefs.primary)
```

#### 关键规则

- 所有颜色值仅存在于 CSS 变量中，TS 代码只能通过 `cssVarRefs` 引用
- 每个主题块必须包含**完整的变量集**（禁止部分覆盖导致样式断裂）
- 启动时在 HTML `<head>` 内联脚本提前设置主题，防止闪烁
- 跨 WebView 同步（主窗口 ↔ 助手窗口）通过 `storage` 事件

### 7. 序号编辑弹窗（Sequence Index Popover）

**规模**：6 文件 / ~291 行

#### 设计原则

这是编辑分镜镜号、片段播放序号的**唯一 UI 入口**（INV-UI-SEQ）。任何模块不得使用居中 Modal 来输入序号。

- **Popover 形式**：浮动在目标位置附近，不阻断用户对画布的感知
- **模式抽象**：支持分镜镜号（严格模式）和片段播放序（允许间隙模式）
- **边界钳制**：`clampSequenceTargetIndex` 确保输入值在有效范围

## 第二部分：AI 任务基础设施

### 8. AI 任务状态机（AI Task System）

**规模**：~189 文件 / ~20,624 行（Rust 4,915 + TypeScript 15,709）

#### 状态机流转

```
submitted → queued → dispatching → running → succeeded
                                            → failed
                                            → cancelled
```

#### Rust 端架构

```
AiQueueFacade (门面)
    ├── Scheduler (定时轮询)
    ├── HandlerRegistry (处理注册表)
    │   ├── text_handler
    │   ├── image_handler
    │   ├── video_handler
    │   ├── tts_handler
    │   └── ... (17+ 处理器)
    ├── state_machine (状态转换守卫)
    └── repo_bridge (持久化适配)
```

#### 核心设计模式

| 模式 | 说明 |
|------|------|
| **门面模式** | `AiQueueFacade` 是唯一入口，外部只需调用 `submit_task`/`cancel_task`/`retry_task` |
| **状态守卫** | 禁止直接写状态字段，所有转换必须经过 `validate_transition` |
| **处理器注册** | 新增 AI 任务类型只需实现 `AiTaskHandler` 并注册，队列逻辑零修改 |
| **终端刷新 Hub** | `useTaskTerminalHub` 周期性轮询 AI 任务表，检测终态边沿变化，分发给注册的刷新处理 |
| **实体宿主锁** | `entity-host-ai-task` 根据当前运行的任务类型锁定对应 UI 表面（表单/画布/主操作按钮） |
| **启动恢复** | `ai-task-boot` 匹配上次未完成的任务与当前故事状态，恢复轮询 |

#### 错误归一化（provider_error_catalog）

```
厂商原始错误                     归一化输出
─────────                       ────────
即梦: {"code":50412}     →     category: "提示词风险"
                                user_hint: "请修改提示词后重试"
可灵: {"code":1002}      →     category: "密钥无效"
                                user_hint: "请检查 Access Key"
通义: HTTP 401           →     category: "认证失败"
                                user_hint: "API Key 已过期"
```

所有错误经 `__BGX_ERR_JSON__` 线格式传输，前端 `resolveAiTaskFailureDisplay` 统一解析为中文提示。

### 9. 提示词专家注入（Prompt Expert）

**规模**：8 文件 / ~1,350 行（纯 Rust，无 TS 副本）

#### 架构

```
attach_prompt_expert_vars(slot, style_domain, genre_id)   ← 唯一入口
    │
    ├── gate: style_expert_injection_enabled()?            ← 总开关
    │
    ├── resolve_styled(style_domain)                       ← 按风格匹配
    │   └── slot 定义 → ExpertSlotDef → 专家身份文本
    │
    ├── resolve_generic()                                  ← 通用兜底
    │
    └── legacy_neutral                                     ← 关闭时中性文本
```

#### 设计特点

- **槽位驱动**：28 个 `PromptExpertSlot`（如 `RolePortraitStageA`、`StoryboardRender`、`VideoOptimize`），每个槽位有一个独一专家身份
- **三级解析**：风格匹配 → 通用兜底 → Legacy 中性
- **运行时开关**：通过 `config.toml` 或环境变量 `BGXIONG_PROMPT_EXPERT=0` 可完全关闭
- **轴注册表**：风格轴和类型轴使用查找表（Map）而非枚举，新增风格无需改核心代码

### 10. 软等待文案（Soft Wait）

**规模**：~16 文件 / ~751 行（Rust 242 + TypeScript 509）

#### 架构

```
云端服务器（BigBearCloud）
    │ ETag 条件请求
    ▼
Rust: pull_soft_wait_texts  ← HTTP + ETag 缓存
    │ IPC
    ▼
TS: cloudSync.ts  ← 云端拉取 + 合并
    │
    ├── localStorage 缓存
    │
    └── defaults.ts  ← 内置兜底文案
         │
         ▼
    useSoftWaitRotating()  ← 轮播 Hook
```

#### 设计特点

- **三级回退**：云端内容 > localStorage 缓存 > 内置默认文案
- **ETag 条件请求**：内容未变化时返回 304，零流量消耗
- **自动轮播**：在指定间隔内循环展示不同的等待文案

### 11. 参考图策略引擎（Pad Policy）

**规模**：~53 文件 / ~8,103 行（Rust ~6,571 + TypeScript ~1,532）

#### 核心概念

"Pad" 是生成 AI 图片时附带的参考图。引擎决定：**用哪些图、怎么编号、如何绑定到 AI 提示词中**。

#### 架构

```
materialize(profile_id, scope)
    │
    ├── pad_reference_inventory  ← 盘点所有可用参考图
    │   ├── 角色定妆图（自动绑定）
    │   ├── 场次概念图（上游传入）
    │   ├── 画布入边图（图连接自动）
    │   └── 手动选择的图
    │
    ├── dismissal               ← 应用隐藏/解除策略
    │
    ├── binding_mode 解析       ← Strict（实体绑定）vs Descriptive（语义描述）
    │
    └── LLM 格式化              ← 生成为 AI 可理解的编号文本
```

#### 设计特点

- **Envelope 模式**：参考图状态封装为 JSON Envelope 嵌入宿主节点内容，读写时合并/提取
- **基于 Profile 物化**：不同场景（分镜/角色定妆/演员/视觉资产）有不同策略
- **补丁式变更**：修改操作（隐藏/显示/手动选择）以补丁形式应用，避免全量重写

## 第三部分：数据与存储基础设施

### 12. 图像版本存储（Image Versions）

**规模**：~1,776 行（Rust ~1,184 + TypeScript ~592）

#### 数据模型

```
node.image_versions (JSON 列)
    └── [
        {
            id, ts, provider, styleDomain,
            images: [
                { id, url?, localCachePath?, hue, direction? }
            ]
        }
    ]
```

#### 功能

- **版本管理**：每次生成存为一个版本，可切换、对比、设为默认

- **默认图选取**：用户可指定某张图作为默认，否则取最新版本的最后一帧
- **LRU 解析缓存**：`parseImageVersionsJson` 带缓存，避免重复解析大 JSON

### 13. 文本自动保存（Content Autosave）

**规模**：~379 行（纯 TypeScript）

```
persisted ◄─── draft ───► history
  │             │            │
  │    (自动保存) │  (手动保存) │
  └─────────────┘            │
                             │
```

#### 设计模式

### 17. 应用更新（App Update）

**规模**：~2,045 行（Rust ~558 + TypeScript ~1,487）

#### 架构

```
启动时（唯一一次 HTTP 检查）
    │
    ├── 强制更新？→ 立即下载 → 全屏阻断 → 安装
    │
    └── 普通更新？→ 后台轮询（3600s 间隔）
                    → 后台下载（Range + 续传 + SHA256 校验）
                    → 右下角浮窗通知 → 用户主动安装
```

#### 关键规则

- **启动检查仅一次**：`BOOT_OUTCOME: OnceCell` 确保每进程生命周期至多 1 次 HTTP 检查
- **强制更新阻断**：`mandatory` 时挂载 `AppUpdateMandatoryGate` 全屏阻断，不渲染主应用树
- **普通更新可关闭**：10 分钟冷却期后可再次弹窗
- **后台下载不阻塞 UI**：Range 分块 + SHA256 异步校验

### 19. 权限管控（Auth & Authz）

**规模**：~4,775 行（Rust 3,423 + TypeScript 1,352）

## 第八节：设计理念总结

全仓 25 个通用模块围绕 **五个核心原则** 构建：

| 原则 | 解释 | 体现 |
|------|------|------|
| **SSOT（单一数据源）** | 每种数据/逻辑只有一个权威位置 | 排版用 CSS 变量、主题用 `:root`、设置用 SQLite、AI 能力用 `model_capabilities` |
| **前端薄编排** | 前端只做参数组装和展示，重计算放 Rust | 端口布局、缩略图生成、文档解析全部在 Rust 完成 |
| **声明式注册** | 新增能力只需声明，不需改核心逻辑 | 厂商模板、Lane 定义、Handler 注册、Transformer 注册 |
| **门禁自动化** | 规则不靠人记，靠脚本检查 | 140+ SSOT 合规脚本覆盖所有模块 |
| **破坏性修复许可** | 发现设计缺陷彻底重写，不堆补丁 | 禁止兼容兜底、禁止双路径、禁止静默降级 |

**一句话概括**：这些通用模块构成了项目的"骨架"——业务模块（故事、角色、分镜等）是"肌肉"，骨架决定了肌肉能发挥多大的力量。骨架设计得好，新增一个业务功能的成本就很低；设计得差，每加一个功能都要重新造轮子。
